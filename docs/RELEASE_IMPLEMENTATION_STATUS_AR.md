# تقرير تنفيذ ومراجعة نسخة Just-M

**تاريخ المراجعة:** 2026-11-04  
**النسخة الأساسية:** `justmNewAppBackup-04-11-2026_v2.zip`

## ما تم دمجه

1. دمج تحديث المرحلة 15 للمحاسبة العامة في ملفات التشغيل الحالية، مع الإبقاء على تعديلات النسخة الأحدث في نقاط التحصيل التي لا تتعارض مع التصحيح.
2. توحيد إثبات تحصيل المبيعات المباشرة في الأستاذ العام عبر `directSalePayment()` داخل معاملة تسجيل التحصيل، بما يشمل حركة المنتجات ورسوم الشحن عندما تكون حركة الشحن منفصلة.
3. فصل إيراد المنتجات عن إيراد الشحن؛ رسوم الشحن تثبت مرة واحدة على مستوى الطلب وبحساب `SHIPPING_REVENUE` مستقل.
4. منع ترحيل البيع إذا كان أي سطر تم تسليمه يفتقد تكلفة وحدة صالحة موجبة. لم يتم تغيير طريقة تقييم المخزون القديمة أو تعبئة تكاليف تاريخية تخمينية.
5. إضافة Migration غير هدام لمواءمة أعمدة ربط القيود وتكلفة سطر الطلب.
6. إضافة Seed مستقل لدليل الحسابات وربط الحسابات النظامية. لا ينشئ أرصدة افتتاحية ولا يربط الصناديق أو وسائل الدفع بمعرفات افتراضية.
7. إصلاح أخطاء صياغة PHP في `DataTables.ssp.php` و`returnSelse_BE.php`.
8. تعطيل مرسل البريد القديم الذي كان يحتوي بيانات SMTP ثابتة ومكشوفة، واستبداله برسالة إعداد واضحة إلى أن يتم إعداد SMTP بطريقة آمنة.
9. تحويل `inc/Classes/dberror.php` إلى `dberror.csv` لأنه ملف بيانات رسائل HTML/CSV وليس ملف PHP.

2. مراجعة وتشغيل Migration المرحلة 15.
3. مراجعة جداول الحسابات وقيود اليومية ثم تشغيل Seed دليل الحسابات.
4. إعداد حسابات الخزائن والبنوك وطرق الدفع لكل فرع في `cash_boxes` و`payment_method_accounts` بمعرفات قاعدة البيانات الفعلية.
5. اختبار دورة بيع وتحصيل ومرتجع ومندوب ومورد على قاعدة اختبار قبل الإنتاج.

لا تشغّل Seed أو Migration على قاعدة الإنتاج قبل مراجعة نسخة احتياطية ومطابقة أسماء الجداول والأعمدة الفعلية.

## ما لم يتم تنفيذه لعدم كفاية معلومات آمنة

1. **مقدم العميل عند إلغاء طلب قبل التسليم:** القرار الوظيفي المعتمد هو تحويل المقدم إلى رصيد دائن للعميل. لكن الفحص أظهر أن مسار التحصيل الحالي يسجل تحصيل البيع بعد التسليم فقط؛ لا يوجد حتى الآن مسار مكتمل لتسجيل مقدم قبل التسليم وربطه بأمر البيع ووسيلة الدفع. لذلك لم يتم تمرير قيد أو إنشاء رصيد افتراضي بلا حركة قبض أصلية. يلزم استكمال دورة قبض المقدم ثم تحويله لرصيد قابل للاستخدام في طلب لاحق.
2. **التحصيل FIFO ورصيد العميل الدائن:** توجد طبقة تخصيصات محاسبية لتحصيل البيع، لكن تطبيق استخدام رصيد العميل على طلب جديد يحتاج شاشة/خطوة تخصيص واضحة وربطًا واختبارًا تكامليًا.
3. **مشتريات الموردين ومردوداتها محاسبياً:** تم تفعيل تخصيص دفعات الموردين تشغيليًا على مستوى الفواتير والمقدم في المرحلة 16، لكن دورة القيود المحاسبية للمشتريات والمردودات ما زالت تحتاج إعداد حساب الموردين واختبارًا تكامليًا على schema مطابق.
4. **تفعيل جميع الشاشات المالية الجديدة:** بعض الكلاسات/الشاشات ما زالت placeholders؛ لم يتم تقديم واجهات شكلية على أنها وظائف مكتملة.
