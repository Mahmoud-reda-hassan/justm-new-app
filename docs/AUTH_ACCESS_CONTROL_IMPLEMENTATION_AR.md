# تأسيس الهوية والصلاحيات — النسخة الأولى

**الحالة:** تنفيذ أولي على الفرع `rebuild-v2`، وليس جاهزًا للنشر الإنتاجي بعد.

## ما تم بناؤه

- تسجيل دخول وخروج باستخدام Laravel Session وواجهة دخول عربية RTL.
- تخزين كلمة المرور باستخدام Hashing الخاص بـ Laravel، وتجديد الجلسة بعد الدخول، وإبطالها عند الخروج.
- تحديد معدل محاولات الدخول بخمس محاولات في الدقيقة لكل اسم مستخدم وعنوان IP.
- إيقاف دخول الحساب غير النشط.
- فصل `account_type` عن الأدوار الإدارية؛ نوع الحساب يصف طبيعة الحساب ولا يمنحه صلاحيات تلقائيًا.
- إسناد المستخدم إلى مجموعة/مجموعات أدوار، وإسناد الصلاحيات إلى الدور.
- فحص الصلاحية من الخادم عبر middleware باسم `permission`، والرفض افتراضيًا عند عدم وجود إسناد.
- جدول نطاقات بيانات صريحة للمستخدم، مع رفض أي نوع نطاق غير معروف. الأنواع الأولية: الشركة، الفرع، المخزن، المندوب الداخلي، وشركة الشحن الخارجية.
- جدول أولي لتسجيل أحداث تغييرات الصلاحيات.
- مفاتيح مستقلة لإدارة الشركات والفروع والمخازن (مشاهدة/إنشاء/تعديل/تفعيل أو إيقاف)، ولا يحصل أي مستخدم عليها تلقائيًا.
- إسناد نطاقات بيانات الشركة والفرع والمخزن للمستخدمين من شاشة إدارة المستخدمين، مع سجل تدقيق لتغيير النطاقات.
- وراثة النطاق: نطاق الشركة يشمل فروعها ومخازنها، ونطاق الفرع يشمل مخازنه، ونطاق المخزن يقتصر على المخزن نفسه. لا يمنح امتلاك صلاحية الشاشة وحده حق الوصول إلى كل السجلات.
- أضيفت صلاحية `permissions.catalog.assign` لتفويض مفاتيح الصلاحيات المتاحة لمجموعات الصلاحيات، وصلاحية `structure.scope.manage_all` لإدارة نطاق الهيكل بالكامل. كلتاهما ضمن إدارة الوصول ولا تمنحان صلاحيات تشغيلية للشركات أو الفروع أو المخازن.

## ما تم تعلمه من النظام القديم

- كان المستخدم يجمع بين بيانات الدخول ونوع الحساب (إدارة، تاجر، مسوق، وسيط، مندوب) والفرع.
- كانت الصلاحيات تحفظ ضمن `USER_SCRIPT` بصيغة PHP serialized داخل مجموعة المستخدمين.
- كلمة المرور القديمة كانت تستخدم MD5، وهو غير مناسب للاستمرار في النظام الجديد.
- النموذج الجديد لا ينقل صيغة `USER_SCRIPT` ولا يحولها تلقائيًا؛ يجب بناء تحويل مضبوط بعد اعتماد قاموس مفاتيح الصلاحيات وربط كل صلاحية بوظيفتها الجديدة.
- لا يتم نسخ صلاحيات النظام القديم أو افتراض أن مجموعة Administrator القديمة تصلح كإعداد افتراضي آمن.

## حدود التنفيذ الحالي

### المنفذ
- تسجيل الدخول والخروج والتحقق من حالة المستخدم.
- إدارة المستخدمين ومجموعات الصلاحيات من واجهات الإدارة.
- إدارة الشركات والفروع والمخازن بواجهات عرض وإضافة وتعديل وتفعيل/إيقاف، مع تقييد القراءة والكتابة بنطاق البيانات.
- إنشاء وتعديل المستخدم، التفعيل/الإيقاف، إعادة تعيين كلمة المرور، وإسناد المجموعات.
- إنشاء وتعديل مجموعات الصلاحيات وإسناد مفاتيح الصلاحيات المتاحة.
- Middleware للتحقق من الصلاحية على الخادم.
- فصل صلاحيات الوظيفة عن نطاق الوصول إلى البيانات.
- تسجيل عمليات إدارة المستخدمين والمجموعات والصلاحيات في سجل التدقيق.
- إنشاء أول مدير عبر نموذج التهيئة الموحّد مع بيانات المؤسسة والفرع الرئيسي والمخزن، وربطه بمجموعة محدودة لإدارة الوصول فقط.
- البريد الإلكتروني للمدير الأول إلزامي وفريد، ويُرسل إليه رابط تحقق موقّع بعد الإنشاء.
- تنفيذ تحقق البريد، وإعادة إرسال رابط التحقق، وتحديث البريد الشخصي بعد تأكيد كلمة المرور الحالية.
- تنفيذ طلب إعادة تعيين كلمة المرور وتعيينها برمز مؤقت، مع رفض الإرسال وإعادة التعيين للحسابات غير النشطة أو البريد غير الموثق.

### غير مكتمل
- لا توجد بعد مفاتيح صلاحيات معتمدة لوحدات المبيعات والمخزون والشحن والحسابات؛ تُحدد عند تحليل كل وحدة.
- لا يوجد استيراد لحسابات النظام القديم أو تحويل تلقائي لـ `USER_SCRIPT`.
- إعداد SMTP في الاستضافة شرط تشغيلي لإيصال رسائل التحقق وإعادة التعيين؛ لا يكفي وضع `MAIL_MAILER=log`.
- نطاقات الشركة/الفرع/المخزن مطبقة في وحدة الهيكل الإداري الحالية فقط؛ يجب إعادة استخدام القاعدة نفسها وتوسيعها عند بناء وحدات الأعمال، وعدم اعتبارها مكتملة على مستوى النظام كله.
- لا تعني إدارة الوصول الحالية اكتمال جميع سيناريوهات الفصل بين المهام أو مراجعة أمنية شاملة.

لا تُعد هذه القائمة بديلًا عن مراجعة الكود والاختبارات على أحدث commit. راجع [AI_WORK_RULES_AR.md](AI_WORK_RULES_AR.md) و[AI_BUILD.md](AI_BUILD.md) لمعرفة قواعد تحديث الحالة.

## الاختبارات

تغطي اختبارات Feature تسجيل الدخول والخروج، ومنع الحساب الموقوف، وإسناد الصلاحية عبر دور نشط، ورفض النطاق غير المسند. يجب اعتماد نتيجة GitHub Actions للالتزام الأحدث قبل اعتبار هذه الاختبارات ناجحة.

## ضوابط النشر

لا تشغّل migrations على قاعدة بيانات حقيقية، ولا تستورد المستخدمين، ولا تنشر التطبيق قبل مراجعة مخطط قاعدة البيانات المستهدف واعتماد خطة تحويل الحسابات والصلاحيات.


## تحديث وحدة التهيئة — 2026-11-09

- أصبح إنشاء أول مدير متاحًا عبر الأمر الطرفي `php artisan justm:provision-first-admin` بعد تشغيل `php artisan justm:setup`.
- المدير الأول يرتبط بمجموعة `system-access-admin` التي تحتوي فقط على صلاحيات إدارة المستخدمين ومجموعات الصلاحيات المعتمدة حاليًا؛ لا يحصل على صلاحيات شاملة أو مالية أو مخزنية.
- كلمة المرور تُطلب بشكل مخفي وتُخزن باستخدام Laravel Hash، ولا توجد بيانات دخول افتراضية.
- يمنع الأمر إنشاء مدير أول إذا كان أي مستخدم موجودًا بالفعل.
- تفاصيل إنشاء قاعدة البيانات والجداول والبيانات الأولية في [SETUP_GUIDE_AR.md](SETUP_GUIDE_AR.md).


## مراجعة أمنية وظيفية — 2026-11-10

- **منفذ:** إسناد مجموعات الصلاحيات للمستخدم يرفض الآن المجموعة غير النشطة على مستوى التحقق الخادمي، وليس اعتمادًا على إخفائها من شاشة الاختيار فقط.
- **السبب:** منع إسناد مجموعة معطلة عبر طلب يدوي ثم منحها صلاحيات مستقبلًا إذا أعيد تفعيلها.
- **اختبار مضاف:** test_inactive_role_cannot_be_assigned_to_a_user ضمن tests/Feature/AccessControlManagementTest.php.
- **التحقق:** نتيجة CI للـ commit الذي يتضمن التغيير مطلوبة قبل اعتبار الاختبار ناجحًا.


## تحديث التحقق بالبريد واستعادة كلمة المرور — 2026-11-10

- أضيف `email_verified_at` إلى المستخدمين عبر Migration مستقلة حتى لا تتطلب إعادة كتابة Migration سبق تشغيلها.
- أضيف جدول `password_reset_tokens` المتوافق مع Laravel Password Broker.
- رابط التحقق موقّع ومحدد المعدل، ويمكن فتحه دون جلسة دخول، مع التحقق من تطابق hash البريد.
- طلب استعادة كلمة المرور لا يرسل رابطًا إلا لحساب نشط وبريد موثق، مع رسالة عامة لا تكشف وجود الحساب.
- المستخدم الذي لا يملك بريدًا أو لم يوثقه يستطيع تحديث البريد من صفحة الحساب بعد إدخال كلمة مروره الحالية، ثم يستقبل رابط تحقق جديدًا.
- اختبار التحقق والتوقيع، ومنع الاستعادة قبل التوثيق، وإتمام الاستعادة، وتحديث البريد قيد التحقق عبر CI.


## تنفيذ إدارة الهيكل الإداري ونطاقات البيانات — 2026-11-10

- أضيفت Migration مستقلة لمفاتيح صلاحيات الشركات والفروع والمخازن، دون تعديل migrations سبق تشغيلها.
- الصلاحيات المنفذة: `companies.view/create/update/activate`، و`branches.view/create/update/activate`، و`warehouses.view/create/update/activate`.
- أضيفت صلاحية `users.assign_scopes` لإسناد نطاقات البيانات، وصلاحية `structure.scope.manage_all` لإدارة نطاق الهيكل بالكامل، وصلاحية `permissions.catalog.assign` لتفويض مفاتيح الصلاحيات المتاحة.
- أضيفت واجهات الهيكل الإداري وروابطها في لوحة التحكم، مع حماية كل مسار على الخادم.
- مدير إدارة الوصول الأول لا يحصل على مفاتيح تشغيل الشركات أو الفروع أو المخازن؛ يمكنه تفويضها إلى مجموعة أخرى، وتعيين نطاقات بيانات المستخدمين.
- قواعد منع الإيقاف: لا توقف شركة لديها فروع نشطة، ولا فرعًا لديه مخازن نشطة؛ لا يمكن إعادة تفعيل فرع أو مخزن إذا كانت الشركة أو الفرع الأب موقوفًا. لا يوجد حذف فعلي.
- خدمة `BranchManager` تظل المسار الوحيد لإنشاء/تعديل الفروع؛ تمنع نقل فرع مرتبط بمخازن وتضمن فرعًا رئيسيًا واحدًا عند تعيينه.
- أضيفت اختبارات Feature لإلزام الصلاحيات، وتقييد نطاق الشركة، وإنشاء الفروع، ومنع نقل فرع مرتبط بمخازن، ومنع إيقاف شركة لديها فروع نشطة، وتدقيق تغيير نطاق المستخدم.
- **حالة الاختبار:** أضيفت الاختبارات إلى المستودع، لكن لم تُشغّل محليًا في هذه الجلسة. يلزم انتظار CI على HEAD الحالي ومراجعة أي إخفاق قبل اعتبار التنفيذ مختبرًا.
- لم تُشغّل Migration أو Seeder على قاعدة الاستضافة، ولم يحدث نشر أو دمج إلى `main`.
