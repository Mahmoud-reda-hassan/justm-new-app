# المرحلة 23 — تصميم الحسابات البنكية وربط وسائل الدفع

**الحالة:** مؤجل — جدول `banks` القديم غير مستخدم حسب تأكيد المستخدم، ولا يُعتمد أساسًا لتصميم أو ترحيل النظام الجديد.  
**التاريخ:** 2026-11-08  
**المرجع:** فرع main وقت إعداد الوثيقة.

## 1. نتيجة فحص الاستخدام الفعلي

- أكد المستخدم أن جدول `banks` في النظام القديم لم يُستخدم فعليًا.
- البحث في المستودع لم يثبت أي مستهلك PHP تشغيلي لجدول `banks`؛ ملف `Bank.php` فارغ، وظهور الجدول محصور في Installer والوثائق.
- لذلك لا تُنقل بيانات الجدول القديم، ولا يُصلح، ولا يُستخدم أساسًا لتصميم النظام المحاسبي الجديد.
- مسارات القبض والصرف الجديدة الحالية تعتمد على `journal_entries` و`journal_entry_details`، وتستخدم `cash_boxes` و`payment_method_accounts` لاختيار حسابات القبض/الصرف.
- مسار تسوية عهدة المندوب وصرف عمولته يختار خزينة فعلية ويتحقق من تطابق الفرع والحساب، ويحفظ `cash_box_id` في سطر القيد؛ هذا مسار نقدي وليس إدارة حسابات بنكية.
- طرق الدفع البنكية/الإلكترونية لا يكفي اسمها وحده لإثبات أن المبلغ وصل إلى حساب بنكي محدد. يجب التمييز بين حساب البنك الفعلي وحسابات التسوية/المستحقات للبوابات والمحافظ والبطاقات.

## 2. الاستنتاج المحاسبي

**التوصية:** النظام المحاسبي الجديد يحتاج كيانًا مستقلًا لإدارة الحسابات البنكية الفعلية، لكنه يجب أن يُبنى من الصفر ضمن المعمارية الجديدة، وليس بإحياء جدول `banks` القديم.

السبب: النظام الجديد يحتاج أن يحدد أين استقرت الأموال فعليًا، ويفصل بين:
1. خزينة نقدية فعلية.
2. حساب بنكي فعلي.
3. حساب وسيط/مستحقات بوابة دفع أو محفظة أو بطاقات، إلى أن تتم التسوية للبنك.

لا يُعامل كل تحويل بنكي أو بطاقة أو محفظة على أنه رصيد بنك مباشر دون معرفة وجهة التسوية.

## 3. التصميم المستهدف المقترح — لا يزال بانتظار اعتماد التفاصيل

### 3.1 كيان الحساب البنكي الجديد

إنشاء `bank_accounts` ككيان جديد مستقل، يحتوي مبدئيًا على:
- `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY`
- `branch_id INT NULL` حسب ملكية الحساب: فرع محدد أو حساب مركزي للشركة.
- `account_id BIGINT UNSIGNED NOT NULL` مرتبط بحساب الأستاذ العام.
- اسم البنك واسم الحساب ورقم الحساب/IBAN وSWIFT وحالة النشاط.
- بيانات العملة بعد حسم سياسة العملات المتعددة.

لا يُنسخ أي سجل من `banks` القديم. ولا تُنشأ حسابات أو أرصدة افتتاحية افتراضية.

### 3.2 اختيار وجهة القبض والصرف

كل مستند قبض أو صرف في النظام الجديد يحدد وجهة مالية فعلية:
- خزينة: `cash_box_id`.
- بنك: `bank_account_id`.
- حساب تسوية/مستحقات: مرجع حساب GL مناسب، مع مستند تسوية لاحق عند انتقال الأموال.

يجب أن يمنع النظام اختيار أكثر من وجهة مالية لنفس سطر القيد، ويتحقق من تطابق الفرع وحساب الأستاذ ونوع الوجهة.

### 3.3 طرق الدفع ليست هي الحساب البنكي

طريقة الدفع تصف كيف دفع العميل أو استلم المستفيد (نقدي، تحويل، بطاقة، محفظة، بوابة دفع). أما الوجهة فتحدد أين توجد الأموال فعليًا. لذلك لا يكفي ربط كل طريقة دفع بحساب واحد ثابت؛ قد يكون لطريقة التحويل البنكي أكثر من حساب بنكي مستهدف، وقد تمر البطاقة بحساب مستحقات بوابة قبل البنك.

## 4. نطاق الوظائف البنكية التي ينبغي أن يغطيها النظام الجديد

- تعريف حسابات البنك وربط كل حساب بحساب GL.
- سند قبض/صرف يحدد الحساب البنكي الفعلي.
- تحويل داخلي بين خزينة وبنك أو بين حسابين بنكيين بقيد مزدوج، دون تسجيل إيراد/مصروف.
- تسجيل رسوم التحويل/البنك بشكل منفصل عند وجودها.
- استيراد/تسجيل كشف البنك ومطابقته مع الحركات الدفترية (Bank Reconciliation).
- تسوية مستحقات البطاقات والمحافظ والبوابات إلى البنك.
- منع الصرف بما يتجاوز الرصيد المتاح وفق سياسة الحساب المعتمدة.

هذه وظائف للنظام الجديد، وليست وظائف ثبت وجودها في النظام القديم.

## 5. ما لم يُنفذ بعد

- لم يُنشأ جدول `bank_accounts` أو Migration.
- لم يُضف `bank_account_id` إلى `journal_entry_details`.
- لم تُعدّل `payment_method_accounts` أو قيود التفرد الخاصة بها.
- لم تُنشأ شاشات سندات بنكية أو تحويل أو مطابقة كشف.
- لم تُشغّل أي SQL على testar أو الإنتاج، ولم يتم نشر تغييرات.

**قرار السلامة:** لا تُنفذ تغييرات SQL أو PHP قبل اعتماد نطاق وظائف البنك والعملة وملكية الحسابات، ثم تنفيذها كجزء من النظام المحاسبي الجديد مع اختبارات MariaDB 10.5.
