# المرحلة 24 — منع تكرار تأكيد الشحنة عند إعادة إرسال الطلب

## الهدف

منع تنفيذ تأكيد الشحنة مرتين عندما يصل نفس طلب HTTP أكثر من مرة (مثل انتهاء مهلة المتصفح بعد أن يكون الخادم قد نفذ العملية)، مع السماح بمحاولة توصيل جديدة فعلية للطلب نفسه.

## التغييرات المنفذة

### 1. الواجهة — `dist/js/model/shipmentDelivery.js`

- توليد `request_key` ثابت لنفس بيانات التأكيد باستخدام `sessionStorage`.
- مفتاح التخزين مرتبط برقم الأمر وكميات التسليم/الرفض ونوع المستخدم.
- إعادة استخدام المفتاح عند إعادة فتح التأكيد بنفس البيانات بعد فشل/انقطاع غير محسوم.
- مسح المفتاح بعد استجابة نجاح مؤكدة؛ وبالتالي أي محاولة جديدة بعد نجاح السابقة تحصل على مفتاح جديد.
- إذا تعذر استخدام `sessionStorage`، يتم إنشاء مفتاح مؤقت؛ في هذه الحالة لا تتوفر حماية إعادة المحاولة عبر إعادة فتح النافذة.

### 2. Controller — `inc/controller/shipment.control.php`

تمرير `request_key` إلى كائن تأكيد الشحنة دون تغيير شكل بيانات المنتجات.

### 3. Backend — `inc/controller/BackEnd/shipment_BE.php`

داخل معاملة تأكيد الشحنة:
1. تكوين بصمة SHA-256 من المستخدم والفرع وعلامة استلام المرتجعات ومحتوى عناصر التأكيد.
2. حجز المفتاح في `delivery_confirmation_requests` بحالة `PROCESSING`.
3. إذا وصل المفتاح نفسه ببصمة مختلفة، يتم رفضه.
4. إذا وصل المفتاح نفسه ببصمة مطابقة وحالته `COMPLETED`، يعاد نجاح سابق دون استدعاء الإجراء المخزن مرة أخرى.
5. بعد نجاح `setDeliveryConfirmationOptimized`، تتحول حالة المفتاح إلى `COMPLETED` قبل اعتماد المعاملة.
6. إذا فشلت المعاملة، يتم التراجع عن سجل المفتاح مع بقية تغييرات العملية.

النسخ القديمة من الواجهة التي لا ترسل مفتاحًا تحصل مؤقتًا على مفتاح عشوائي للتوافق، لكنها لا تستفيد من حماية إعادة المحاولة. يجب تحديث ملفات JavaScript في النشر.

### 4. قاعدة البيانات

- إضافة جدول `delivery_confirmation_requests` إلى ملف التثبيت.
- إضافة Migration قابل لإعادة التشغيل:
  `inc/Databases/Migrations/20261105_delivery_confirmation_request_idempotency.sql`

## لماذا لا يمنع هذا محاولة توصيل جديدة؟

المفتاح يُمسح من المتصفح بعد نجاح التأكيد. عند بدء محاولة لاحقة بنفس الكميات، يُنشأ مفتاح جديد؛ لذلك لا يتم دمج محاولتين فعليتين في سجل واحد.

## اختبارات القبول المطلوبة

1. نفس `request_key` ونفس البيانات بعد نجاح العملية: يعاد نجاح العملية السابقة ولا يعاد استدعاء الإجراء المخزن.
2. نفس `request_key` مع تغيير كمية منتج أو المستخدم أو الفرع أو خيار استلام المرتجعات: يرفض الطلب.
3. مفتاح جديد بعد نجاح المحاولة السابقة: يسمح بتنفيذ محاولة توصيل جديدة.
4. فشل الإجراء المخزن: تتراجع المعاملة وسجل المفتاح معًا، ويمكن إعادة الطلب بنفس المفتاح.
5. طلبان متزامنان بنفس المفتاح: القيد الأساسي الفريد يجعل الطلب الثاني ينتظر نتيجة الأول، ثم يعيد النجاح السابق أو ينفذ بعد تراجع الأول.

## حالة التحقق

- تم التحقق من وجود التعديلات على `main` في الملفات الأربعة والـ Migration.
- لم يتم تشغيل PHP lint أو اختبار MariaDB فعلي.
- لم يتم تنفيذ SQL على أي قاعدة بيانات أو نشر على الاستضافة.
- لا تزال حماية النسخ القديمة من الواجهة غير مضمونة حتى تحديث ملفات JavaScript.
- هذه المرحلة تمنع تكرار تأكيد الشحنة نفسه، لكنها لا تنشئ بعد قيد عمولة محاولة الرفض؛ ربط العمولة سيتم على `shipping_movement.shipmov_id` بعد اعتماد مسار المحاولة والـ snapshots.
