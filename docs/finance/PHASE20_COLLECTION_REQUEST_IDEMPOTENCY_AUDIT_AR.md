# تدقيق نطاق منع التكرار لطلبات تحصيل المندوب

**التاريخ:** 2026-11-05  
**الفرع:** main  
**النطاق:** مراجعة ساكنة لـ DeliverySettlementManager وFinancialEventManager.  
**لم يتم تشغيل SQL أو اختبار MariaDB أو النشر.**

## النتيجة

منع التكرار الحالي في registerCustomerCollection يعمل على مستوى كل أمر بيع، وليس على مستوى طلب التحصيل الكامل المرسل من الواجهة.

يُنشأ مفتاح الحدث لكل أمر بالشكل:

DELIVERY_COLLECTION:{requestKey}:ORDER:{orderId}

هذا يحمي إعادة إرسال الأمر نفسه بالمفتاح نفسه، لكنه لا يحجز requestKey على مستوى قائمة الأوامر كاملة.

## سيناريو الخلل

1. إرسال requestKey = K للأمر A.
2. نجاح تسجيل التحصيل.
3. إعادة استخدام K للأمر B بدل A، أو إرسال A مع إضافة B.
4. الحدث الفرعي الخاص بـ B لم يكن موجودًا؛ فيمكن أن ينشئ النظام تحصيلًا جديدًا بدل رفض اختلاف الحمولة الكاملة.

إذًا منع التكرار الحالي لكل أمر منفرد، وليس ضمانًا لثبات مجموعة الأوامر الكاملة.

## المعالجة المطلوبة

إضافة سجل رئيسي لطلب التحصيل بمفتاح فريد وبصمة canonical للحمولة الكاملة. يُنشأ ويُقفل داخل نفس معاملة PDO قبل إنشاء أحداث الأوامر الفرعية.

البصمة تشمل:
- delivery_id
- branch_id
- payment_method_id
- قائمة order_id ومبلغ كل أمر بعد ترتيبها وتوحيد صيغة الأرقام
- note

قواعد السلوك:
- نفس المفتاح ونفس البصمة: إعادة نتيجة الطلب السابق.
- نفس المفتاح وبصمة مختلفة: رفض قبل إنشاء أي مستند فرعي.
- مفتاح جديد: طلب جديد يخضع لفحوص الرصيد المفتوح.

## اختبارات القبول

1. K + A + نفس المبلغ، ثم إعادة نفس الطلب: يعيد المستند السابق.
2. K + A + مبلغ مختلف: رفض.
3. K + B بدل A: رفض.
4. K + A ثم K + A وB: رفض.
5. K + A وB مع تغيير ترتيب العناصر فقط: يعتبر نفس الطلب بعد canonical normalization.
6. K2 + نفس البيانات: طلب مستقل يخضع لفحص المديونية المفتوحة.
7. طلبان متزامنان بالمفتاح نفسه: لا ينتج عنهما أكثر من طلب رئيسي واحد.

## إصلاح منفصل تم تنفيذه

في FinancialEventManager.php، كان كود معالجة تعارض INSERT يحاول إعادة رمي متغير الاستثناء خارج نطاق catch الذي عرّفه. تم حفظ PDOException في متغير واضح وإعادة رميه عند عدم العثور على سجل يحمل مفتاح الحدث نفسه، حتى لا يُخفى سبب قيد فريد آخر خلف متغير غير معرّف.

## نطاق التنفيذ التالي

تنفيذ سجل الطلب الرئيسي كوحدة واحدة:
1. جدول جديد في JUSTM_DATABASE_INSTALL.sql.
2. Migration متوافق مع MariaDB 10.5.
3. تعديل DeliverySettlementManager لإنشاء/قفل سجل الطلب والتحقق من بصمته.
4. إعادة نتيجة الطلب السابق بصورة موحدة.
5. اختبارات MariaDB للتكرار وتغيير الحمولة والتزامن والفشل داخل المعاملة.

لا يكفي تعديل PHP وحده أو إضافة request_key إلى المستندات الفرعية؛ المطلوب حجز المفتاح لمجموعة الأوامر كاملة.

## الحالة

تم حفظ هذا التدقيق وإصلاح FinancialEventManager.php. لم يتم تنفيذ SQL أو اختبار تكاملي أو نشر.
