# مصفوفة الصلاحيات — مسودة تجميعية للمراجعة

> **الحالة والنطاق:** هذه الوثيقة مسودة تحليلية لمصفوفة صلاحيات وحدات الأعمال، وليست قائمة مفاتيح نهائية معتمدة. لا تصف حالة تنفيذ إدارة الوصول الأساسية: تسجيل الدخول وإدارة المستخدمين ومجموعات الصلاحيات وMiddleware وسجل التدقيق نُفذت مبدئيًا على `rebuild-v2` وفق `AUTH_ACCESS_CONTROL_IMPLEMENTATION_AR.md`. مفاتيح صلاحيات المبيعات والمخزون والشحن والحسابات الواردة هنا مقترحات لا تُزرع أو تُعامل كاعتماد قبل تحليل كل وحدة وموافقة المستخدم.


> **تحديث تنفيذ فعلي — 2026-11-10:** على `rebuild-v2` أضيفت مفاتيح تشغيلية أولية لإدارة الهيكل الإداري فقط: `companies.view/create/update/activate`، `branches.view/create/update/activate`، `warehouses.view/create/update/activate`. وأضيفت `users.assign_scopes` و`structure.scope.manage_all` و`permissions.catalog.assign` لإدارة نطاقات الوصول وتفويض مفاتيح الصلاحيات. هذه المفاتيح موجودة في Migration مستقلة وتُختبر عبر Feature tests؛ وجودها لا يعني اعتماد بقية مفاتيح هذه الوثيقة أو تنفيذ وحدات الأعمال. راجع [AUTH_ACCESS_CONTROL_IMPLEMENTATION_AR.md](AUTH_ACCESS_CONTROL_IMPLEMENTATION_AR.md) للتفاصيل.

## 1.1 منهج التصميم الأكاديمي للنظام الجديد

> **قاعدة حاكمة معتمدة في منهج العمل:** نحن نؤسس نظامًا جديدًا من البداية. النظام القديم مصدر أدلة لفهم المجال واكتشاف الحالات الواقعية والمشكلات والاحتياجات، وليس معيارًا ملزمًا للتصميم أو مرجعًا لنسخ صلاحياته أو شاشاته أو إجراءاته.

يُصمم كل مجال وفق منهج تحليل وتصميم نظم مستقل، بالترتيب التالي:

1. **تحليل أصحاب المصلحة والسياق:** تحديد المستخدمين والجهات والأنظمة المتفاعلة واحتياجات كل طرف.
2. **تحليل المتطلبات:** توثيق المتطلبات الوظيفية وغير الوظيفية، والقيود، والأهداف، ومعايير القبول.
3. **نمذجة العمليات:** تحديد بداية العملية ونهايتها، والأحداث، والقرارات، والاستثناءات، والمسارات البديلة، والمسؤوليات.
4. **نمذجة الحالات:** تعريف حالات الكيانات وانتقالاتها المسموحة وشروط كل انتقال، دون استيراد أرقام أو أسماء الحالات القديمة تلقائيًا.
5. **تحليل الصلاحيات:** اشتقاق صلاحيات دقيقة من العمليات والمهام ومبدأ أقل امتياز، مع فصل الواجبات عند وجود مبرر رقابي أو تشغيلي.
6. **تحليل البيانات:** تحديد الكيانات والعلاقات والقيود والتاريخ التشغيلي وسجل التدقيق ومصدر الحقيقة لكل معلومة.
7. **التصميم المعماري:** تحديد حدود الوحدات والمسؤوليات والتكاملات ومنع ازدواج ملكية البيانات.
8. **التحقق:** مراجعة السيناريوهات الطبيعية والاستثنائية، والتعارضات، وسوء الاستخدام، ومتطلبات الأمن والأداء وقابلية الصيانة.
9. **التتبع والاعتماد:** ربط كل متطلب بعملية وصلاحية وبيانات واختبار، وتسجيل قرار الاعتماد قبل التنفيذ.

### كيفية استخدام النظام القديم

- يُراجع القديم لاكتشاف الوظائف والبيانات والحالات والاستثناءات التي قد لا تظهر في الوصف الأولي.
- كل ملاحظة من القديم تصنف كسلوك قديم مثبت، ولا تتحول تلقائيًا إلى متطلب جديد.
- يُقبل السلوك القديم فقط إذا ثبتت الحاجة إليه واتساقه مع أهداف النظام الجديد والمتطلبات المعتمدة.
- يجوز إعادة تصميم العملية أو دمج الشاشات أو فصلها أو تغيير دورة العمل أو الاستغناء عن سلوك قديم، بشرط توثيق السبب والأثر واعتماد التغيير عند تأثيره على قواعد العمل.
- لا يُفترض أن أسماء الأدوار أو الصلاحيات أو الجداول أو الحالات القديمة تمثل أفضل ممارسة.
- المرجع النهائي هو المتطلبات والقرارات المعتمدة للنظام الجديد، لا مجرد التطابق مع القديم.

### مبادئ هندسية حاكمة

- مبدأ أقل امتياز (Least Privilege).
- الفصل بين المهام (Separation of Duties) بحسب المخاطر، دون فرض فصل شكلي غير مبرر.
- الرفض الافتراضي عند غياب التفويض (Deny by Default).
- التحقق من الصلاحية والنطاق على الخادم في كل عملية.
- فصل هوية المستخدم ونوع الحساب عن صلاحياته الإدارية.
- فصل صلاحية الوصول إلى الوظيفة عن نطاق السجلات التي يجوز الوصول إليها.
- قابلية التدقيق والتتبع وعدم محو التاريخ التشغيلي أو المالي.
- البساطة والاتساق وتقليل التكرار، مع عدم التضحية بوضوح المسؤوليات.

## 1. المبادئ الحاكمة

1. يظل نموذج **مجموعات الصلاحيات** هو طريقة إسناد الصلاحيات للمستخدمين، مع إمكانية تخصيص كل مجموعة من مدير النظام.
2. المسمى الوظيفي أو نوع الحساب لا يمنح صلاحيات إدارية تلقائيًا. نوع الحساب (إداري، تاجر، مسوق، وسيط، مندوب، وغيرها) مستقل عن مجموعة الصلاحيات.
3. نفصل بين مشاهدة الشاشة، ومشاهدة السجل، وتنفيذ الإجراء، واعتماد الإجراء، والترحيل/التنفيذ النهائي.
4. الصلاحية لا تكفي وحدها: يجب التحقق من حالة السجل، وصحة انتقال الحالة، والعلاقات، ونطاق الوصول.
5. إخفاء زر أو رابط ليس حماية؛ التفويض يتم على الخادم في كل عملية.
6. لا تُستخدم معرفات الشركة أو الفرع أو المخزن الواردة من المتصفح دون التحقق من نطاق المستخدم والعلاقات.
7. الصلاحيات الحساسة تسجل في سجل تدقيق، مع دعم فصل المهام عندما تفرضه سياسة العمل.
8. لا ننقل أخطاء التنفيذ القديم، ولا ننسخ تخزين PHP serialized؛ تستخدم مفاتيح ثابتة وعلاقات منظمة.

## 2. قاموس الأفعال المقترح

| الفعل | المقصود |
|---|---|
| View | مشاهدة القوائم والبيانات |
| ViewDetails | مشاهدة تفاصيل سجل محدد |
| Create | إنشاء سجل أو مستند |
| Update | تعديل بيانات أو مستند قبل/وفق ضوابط حالته |
| Cancel | إلغاء منطقي أو تحويل لحالة ملغاة، وليس حذفًا تاريخيًا |
| Delete | حذف فعلي محدود للبيانات المرجعية غير المستخدمة فقط |
| Execute | تنفيذ إجراء تشغيلي مثل الصرف أو الاستلام أو التحويل |
| Submit | إرسال للمراجعة أو الاعتماد |
| Review | مراجعة البيانات والتحقق منها |
| Approve | اعتماد قرار أو نتيجة ضمن اختصاص الدور |
| Reject | رفض مع سبب |
| ReturnForCorrection | إعادة المستند بالكامل للتصحيح مع سبب إلزامي |
| Post | ترحيل أثر مالي/مخزني نهائي |
| Settle | تسوية عهدة أو رصيد أو فرق |
| Reconcile | مطابقة مستندات/تحصيلات/توريدات |
| Export | تصدير البيانات |
| ManageSettings | تعديل إعدادات المجال |

ليست كل الأفعال مطلوبة في كل وحدة؛ يتم اختيار الأفعال المناسبة لطبيعة كل عملية.

## 3. مصفوفة الوحدات والإجراءات الأولية

الرموز:
- **م** مشاهدة، **ت** إنشاء، **ع** تعديل، **ل** إلغاء/تعطيل، **ن** تنفيذ، **ر** مراجعة، **ا** اعتماد، **ح** ترحيل، **س** تسوية/مطابقة، **ض** إعدادات.
- العلامة «مستقل» تعني أن الإجراء يجب أن يكون مفتاحًا منفصلًا، لا أنه دور ثابت أو مستخدم بعينه.
- كل صف أدناه يتطلب تطبيق نطاق البيانات المناسب، ما لم يذكر خلاف ذلك.

| الوحدة | الإجراءات التي ينبغي فصلها | ملاحظات التفويض |
|---|---|---|
| لوحة التحكم | مشاهدة المؤشرات، تصدير التقارير | كل مؤشر يخضع لنطاق بياناته وصلاحية مصدره |
| المستخدمون | مشاهدة، إنشاء، تعديل، تفعيل/تعطيل، إعادة تعيين كلمة المرور، إسناد مجموعة، إدارة أنواع الحسابات | منع تصعيد الامتيازات؛ لا يسند المستخدم صلاحيات تتجاوز ما يملكه |
| مجموعات الصلاحيات | مشاهدة المجموعات والمصفوفة، إنشاء، تعديل، تعطيل/حذف آمن، إسناد للمستخدمين | سجل تغييرات؛ حماية المجموعة المرتبطة بمستخدمين |
| العملاء | مشاهدة القائمة والتفاصيل، إنشاء، تعديل الملف، إدارة العناوين والهواتف، تعطيل | نطاق ملكية/شريك عند وجود مسوق أو وسيط؛ لا تخلط إدارة العميل بإنشاء طلب له |
| الموردون | مشاهدة، إنشاء، تعديل الملف، إدارة العناوين والهواتف، تعطيل | منفصل عن صلاحيات الشراء والاستلام والصرف المالي |

| أوامر البيع | مشاهدة القوائم والتفاصيل، إنشاء، تعديل، إلغاء، تغيير الحالة، إرسال للمراجعة، اعتماد، إعادة للتصحيح | تحقق انتقال الحالة؛ اعتماد الأمر بعد التعديل وفق دورة العمل |

## 4. نطاق الوصول للبيانات

النطاق ليس فعلًا واحدًا، بل قيد يطبق مع كل صلاحية مشاهدة أو كتابة أو اعتماد.

| بُعد النطاق | الاستخدام |
|---|---|
| الشركة | شركة واحدة أو الشركات المصرح بها أو جميع الشركات |
| الفرع | فرع واحد أو مجموعة فروع أو جميع الفروع المصرح بها |
| المخزن | مخزن واحد أو مجموعة مخازن أو جميع المخازن المصرح بها |
| الشريك/المالك | العملاء والطلبات التابعة للمسوق/الوسيط/الحساب المسموح |
| صاحب العهدة | المندوب الداخلي أو شركة الشحن الخارجية المرتبطة بالعهدة |
| الحساب/الخزينة | الحسابات والخزائن المصرح بها للمستخدم |
| السجل نفسه | منع الوصول لسجل خارج النطاق حتى لو عرف المستخدم رقمه |

قواعد مقترحة:
- النطاق الفعلي هو تقاطع صلاحية الفعل مع نطاق المستخدم وعلاقات السجل.
- لا يسمح بتوسيع نطاق المستخدم من خلال إرسال معرف بديل في الطلب.
- صلاحية «كل الشركات/الفروع/المخازن» يجب أن تكون صريحة ومحددة، ولا تستنتج من الدور.
- التحقق يتم على الخادم في القراءة والكتابة والتصدير والاعتماد.

## 5. فصل المهام والاعتمادات

هذه ضوابط مرتبطة بالعملية وليست أدوارًا عامة ثابتة:

- أمين المخزن مسؤول عن الاستلام المخزني الكامل، ويجوز له تنفيذ عكس التسوية المخزنية قبل الإغلاق المالي وفق الضوابط المعتمدة.
- يجوز للمسؤول عن التحصيل المالي أيضًا تنفيذ عكس التسوية المخزنية قبل الإغلاق المالي؛ ويظل تنفيذ العكس مقيدًا بتوافر كامل الكمية الحرة، وعدم المساس بحجوزات أو كميات أوامر أخرى، وحفظ السبب والأثر التاريخي.
- المسؤول المالي يعتمد الأثر المالي والتحميل والتسويات المالية.
- المسؤول المالي يستطيع إعادة أمر العهدة بالكامل للمسؤول المخزني للتصحيح بسبب إلزامي؛ وبعد التصحيح يعود الأمر للمراجعة المالية.
- يمكن لمستخدم واحد الجمع بين صلاحيات المسؤول المخزني وأمين المخزن إذا أسندت له المجموعتان/الصلاحيات؛ لا نفرض فصلًا وظيفيًا مطلقًا.
- إعدادات اعتماد رد المبالغ تدعم مستوى واحدًا أو عدة مستويات، وحدود مبالغ، وتحديد الأدوار/المستخدمين، ومنع المنشئ من الاعتماد أو اشتراط اختلاف المعتمدين حسب السياسة.
- لا ينشأ أثر مالي نهائي من إجراء مخزني وحده، ولا تنشأ حركة مخزنية من اعتماد مالي وحده.

## 6. حالات خاصة لا تختزل إلى CRUD

1. **أمر البيع:** تعديل البيانات لا يعني اعتمادها؛ يلزم مسار اعتماد بعد التعديل.
2. **الحجز:** الحجز يبدأ عند إنشاء الطلب، لكن الاحتفاظ به وتأثير الحالة على المتاح تحددهما إعدادات المخزون المحتجز.
3. **عهدة الشحن:** حالة الطلب منفصلة عن حيازة المنتجات؛ استرداد الطلب لا يعني بالضرورة عودة المنتجات للمخزن.
4. **عكس التسوية المخزنية:** إجراء إلزامي عند كل إعادة رسمية للتصحيح بعد اكتمال التسوية وقبل الإغلاق المالي؛ لا يسمح بالتصحيح دون العكس حتى إذا لم تتغير الكميات. ينفذه أمين المخزن أو المسؤول عن التحصيل المالي وفق الصلاحية، ويعيد المنتجات المستلمة إلى جهة التوصيل بحركة صرف مرتبطة بعكس الاستلام، بعد التحقق من توافر كامل الكمية الحرة.
5. **شركة الشحن:** تقرير التوصيل لا ينشئ دخولًا مخزنيًا ولا يثبت قبض الشركة للمبالغ.
6. **المرتجع:** لا يعاد المنتج للمتاح إلا بعد الاستلام الفعلي والفحص والاعتماد.
7. **الإعدادات:** يجب حفظ نسخة السياسة/القيمة التي طبقت على المستند وقت إنشائه أو اعتماده عندما يكون للتغيير أثر تاريخي.

## 7. عناصر لم تحسم بعد

- القائمة النهائية لمفاتيح الصلاحيات الدقيقة وتسمياتها الثابتة.
- هل يتم تعطيل الكيانات المرجعية دائمًا أم يسمح بحذف فعلي في حالات محددة.
- الصلاحيات التفصيلية لكل شاشة إعدادات عامة، بعد اكتمال جردها.
- من يملك اعتماد التغييرات الحساسة في إعدادات المخزون والشحن والحسابات.
- مصفوفة الأدوار الافتراضية المقترحة للمستخدمين الجدد؛ لم تعتمد بعد.
- قواعد التفويض الدقيقة للتاجر والمسوق والوسيط والمندوب والعملاء المسجلين.
- حدود تصدير البيانات الحساسة وسجل التدقيق.
- الصلاحيات النهائية للتكاملات والمهام الآلية.
- تفاصيل مفاتيح إدارة الحسابات والأستاذ العام وفق وثائق المجال المالي على الفرع المرجعي.

- لا تستخدم أرقام حالات النظام القديم في أسماء المفاتيح؛ الحالات والانتقالات قاموس مستقل.
- المفتاح يخضع أيضًا لنطاق الوصول وحالة السجل وصحة الانتقال وفصل المهام.

- نطاق الشركة والفرع والمخزن والشريك وصاحب العهدة والحساب/الخزينة والسجل يطبق على القراءة والكتابة والاعتماد والتصدير.

## 8. حالة هذه الوثيقة

- الصفوف هي مجموعات إجراءات مقترحة وليست اعتمادًا نهائيًا لكل مفتاح.
- لم يتم إنشاء جداول صلاحيات أو migrations أو Policies أو شاشات.
- لم يتم تنفيذ اختبارات تشغيلية أو أمنية.
- نطاق المستخدمين ومجموعات الصلاحيات أعلاه معتمد كبداية تنفيذية، ويجري تنفيذه واختباره على فرع `rebuild-v2`.

## 7.2 حالات استخدام الصلاحيات لدورة المخزون والعهدة — 2026-11-10

> **الحالة:** تفصيل تحليلي للمصفوفة، وليس اعتمادًا نهائيًا لمفاتيح الصلاحيات. أسماء المفاتيح أدناه أمثلة مرشحة تتبع النمط المبدئي في 7.1. لا تُضاف إلى الكتالوج أو Migration قبل اعتماد الوحدة.

### أ. قواعد التفويض المشتركة

1. كل حالة استخدام تتطلب اجتماع ثلاثة شروط على الخادم: صلاحية الفعل، ونطاق السجل، وصحة حالة المستند/الانتقال. امتلاك اثنين منها لا يعوض غياب الثالث.
2. نطاق المخزون يشمل الشركة والفرع والمخزن؛ ونطاق العهدة يشمل نوع الجهة وصاحب العهدة؛ ونطاق أمر البيع/العميل يطبق كذلك عند عرض تفاصيل الطلب. لا يوسع معرف يرسله المتصفح أي نطاق.
3. المشاهدة والتفاصيل والتصدير أفعال مستقلة. إخفاء زر أو رابط ليس تفويضًا.
4. يمكن للمستخدم الجمع بين أكثر من وظيفة إذا أسندت إليه صلاحياتها ونطاقاتها؛ لا يوجد فصل وظيفي مطلق لمجرد المسمى. لكن أي قيد فصل مهام منصوص عليه لعملية بعينها يطبق على الخادم.
5. لا تمنح account_type أو عضوية مجموعة باسم وظيفي أي صلاحية تلقائية. مجموعات الصلاحيات هي وسيلة الإسناد، ومفاتيحها الفعلية هي مصدر التفويض.
6. لا توجد صلاحية حذف لمستندات المخزون أو العهدة أو البيع بعد إنشائها؛ تستخدم إجراءات الإلغاء أو العكس المسموح بها مع الاحتفاظ بالتاريخ.
7. شركة الشحن الخارجية ليست مستخدمًا ينفذ إجراءات داخل النظام؛ الموظف المخول هو الذي يسجل تقريرها ونتائجه ومراجعها.

**ضابط خاص بعكس التسوية:** حق تنفيذ العكس ليس صلاحية عامة لكل من يستطيع مشاهدة العهدة أو استلام المرتجع. يقتصر على من أُسند إليه مفتاح العكس، ويُقبل فقط قبل الإغلاق المالي، وبعد تحقق الكمية الحرة لكل الأصناف. إذا نقص صنف واحد يرفض الإجراء كاملًا دون أثر جزئي. لا يسمح بعكس عكس سابق أو تكرار عكس المستند نفسه.

### د. اختبارات التفويض والأمن المطلوبة

1. مستخدم يملك صلاحية مشاهدة المخزون فقط: يستطيع القراءة ضمن نطاقه، ويرفض الخادم الاستلام والصرف والتحويل والجرد.
2. مستخدم يملك صلاحية استلام مخزن A ونطاقه مخزن A: يرفض استلامًا لمخزن B حتى لو أرسل معرف B يدويًا.
3. مستخدم يملك صلاحية الصرف ولا يملك نطاق الجهة المستلمة: يرفض الصرف إلى مندوب/شركة شحن خارج النطاق.
4. مستخدم يملك صلاحية تسجيل نتيجة التوصيل: لا يستطيع تسجيل نتيجة لأمر مجمد أو عهدة ليست ضمن نطاقه.
5. موظف يسجل تقرير شركة الشحن: لا يؤدي استيراد التقرير إلى إنشاء وارد مخزني أو إثبات توريد نقدي.
6. مستخدم يملك تسجيل الاستلام: لا يستطيع إصدار إذن استلام ثانٍ للأمر أو استلام دفعة إضافية بعد اكتمال الإذن.
7. مستخدم يملك تصحيح نتيجة التسليم: يرفض التصحيح بعد التسوية المخزنية ما لم يسبق ذلك عكس صحيح ومسموح.
8. مستخدم يملك عكس التسوية لكن الأمر مغلق ماليًا: يرفض العكس.
9. مستخدم يملك عكس التسوية والكمية الحرة ناقصة لصنف واحد: يرفض العملية كلها ولا ينشئ حركات لبعض الأصناف.
10. مستخدم يملك مراجعة العهدة دون صلاحية العكس: لا يستطيع تنفيذ العكس باستدعاء endpoint مباشر.
11. مستخدم يملك إنشاء أمر شراء دون صلاحية اعتماد: يستطيع إنشاءه وإرساله حسب السياسة، ولا يستطيع اعتماده.
12. مستخدم يملك تسجيل استلام توريد: لا يستطيع تجاوز الكمية المتبقية أو تكرار الدفعة نفسها.
13. مستخدم يملك تسجيل العد دون اعتماد الفروق: لا يستطيع ترحيل فرق الجرد.
14. مستخدم يملك صلاحية تحويل لمخزن المصدر دون نطاق الوجهة: يرفض التحويل.
15. كل رفض تفويض يسجل الحدث الحساس دون تسريب بيانات السجل غير المصرح به؛ ولا يسجل أي أثر تشغيلي جزئي.

### هـ. نقاط لا يجوز حسمها من الصلاحيات وحدها

- هل يلزم فصل منشئ أمر الشراء عن معتمده؟ وما حدود اعتماد المبالغ؟
- هل استلام التوريد يتطلب فحصًا أو اعتمادًا ثانيًا دائمًا أم حسب نوع الصنف/المورد؟
- هل التحويل داخل الفرع فقط أم بين الفروع؟ ومن يعتمد الاستلام في الوجهة؟
- من ينشئ ويراجع ويعتمد الهالك؟ وما مستند إثباته والحساب المقابل؟
- من يعتمد فروق الجرد، وهل يلزم اعتماد ثانٍ بحسب قيمة الفرق؟
- صلاحيات الحسابات والقبض والصرف والترحيل والعكس تظل مرتبطة باعتماد دورة المحاسبة؛ لا تُستنتج من صلاحيات المخزون.
- مصفوفة المجموعات الافتراضية وتوزيع المفاتيح على المستخدمين لم تعتمد؛ لا تنشأ أدوار ثابتة باسم «أمين مخزن» أو «مدير مالي» بصلاحيات تلقائية.

### و. حالة الاعتماد

- هذا القسم يربط حالات الاستخدام بصلاحيات مرشحة وشروط تحقق واختبارات أمنية.
- لا يعتمد مفاتيح نهائية ولا يغير الكتالوج أو migrations.
- تظل صلاحيات كل فعل منفصلة عن نطاق الوصول، وتظل حالة المستند شرطًا إضافيًا.
- أي تغيير في الصلاحيات الحالية لإدارة الوصول يجب أن يراجع في ضوء تنفيذ AUTH_ACCESS_CONTROL_IMPLEMENTATION_AR.md، خصوصًا حماية مجموعة system-access-admin وآلية تفويض مفاتيح الكتالوج؛ لا يعاد تفسير حماية المجموعة على أنها منع عام للمستخدم من إضافة صلاحيات تشغيلية إلى مجموعته وفق القرار الموثق في تحديث 2026-11-10.


## 7.3 مطابقة حالات الاستخدام مع تنفيذ Laravel الحالي — 2026-11-10

> **الحالة:** مراجعة ساكنة للكود على HEAD وقت الفحص، وليست اختبار اختراق أو اعتمادًا نهائيًا. يظل القسم 7.2 مواصفة حالات الاستخدام، وهذا القسم يصف ما هو موجود فعلًا وما ينقصه.

### أ. حدود التنفيذ الموجودة حاليًا

- مسارات `routes/web.php` الحالية تغطي المصادقة والتحقق من البريد وإدارة قاعدة البيانات وإدارة المستخدمين ومجموعات الصلاحيات وإدارة الشركات والفروع والمخازن.
- يوجد Middleware عام `EnsureUserHasPermission` يتحقق من صلاحية الفعل فقط عبر `User::hasPermission()`. لا يطبق نطاق السجل أو حالة المستند؛ يجب أن يضاف هذان الشرطان داخل كل حالة استخدام/Policy أو خدمة المجال.
- `User::hasPermission()` يشترط أن يكون المستخدم نشطًا، وأن تكون المجموعة المسندة نشطة، ثم يتحقق من مفتاح الصلاحية. لا يمنح `account_type` صلاحيات تلقائية.
- نطاقات الشركة والفرع والمخزن مطبقة حاليًا داخل `OperatingStructureController`، مع توريث نطاق الشركة إلى فروعها ومخازنها، ونطاق الفرع إلى مخازنه.
- حماية `system-access-admin` موجودة في `AccessControlController::assignRolePermissions()`: تسمح لمدير الوصول الأول بإضافة صلاحيات تشغيلية إلى مجموعته، وتحافظ على صلاحيات الإدارة المحمية، وترفض إضافة مفاتيح إدارية حساسة جديدة. اختبارات Feature الحالية تغطي هذه الحالات الأساسية.
- لا توجد حاليًا مسارات أو Controllers أو Models أو migrations تشغيلية للبيع والمخزون والمشتريات والصرف والعهدة والمرتجعات والتسويات. مجلدات Domain/Infrastructure ما زالت placeholders، وملفات اختبارات التكامل/القبول لا تحتوي تنفيذًا لهذه المجالات.

### ب. فجوات مؤكدة في إدارة المستخدمين والنطاقات

1. شاشة المستخدمين في `AccessControlController::users()` تجلب جميع المستخدمين دون تقييدهم بنطاق المستخدم الحالي.
2. عمليات تعديل المستخدم، إيقافه، إعادة تعيين كلمة مروره، إسناد المجموعات، وإسناد النطاقات لا تتحقق من أن المستخدم المستهدف داخل نطاق السجل الذي يسمح به المنفذ. صلاحية الفعل وحدها لا تحقق قاعدة التفويض المشتركة في 7.2.
3. `assignUserScopes()` تتحقق من النطاقات الحالية والجديدة بمطابقة مباشرة عبر `hasDataScope(type,id)`. بخلاف منطق الهيكل التشغيلي، لا تستنتج أن نطاق الشركة يسمح بنطاق فرع تابع لها أو أن نطاق الفرع يسمح بمخازنه؛ قد يمنع ذلك إسناد نطاق فرعي مشروع لمستخدم لديه نطاق أب.
4. `resetUserPassword()` لا تحتوي حماية صريحة من إعادة تعيين المستخدم كلمة مرور حسابه الحالي، بينما توجد حماية ذاتية صريحة في تعديل بيانات الحساب وإيقافه وتغيير مجموعاته. يلزم حسم الاتساق المطلوب قبل التعديل.
5. `storeUser()` يثبت `account_type = admin` لكل مستخدم جديد. هذا لا يمنحه صلاحيات بذاته وفق `hasPermission()`، لكنه يضع نوع حساب إداريًا افتراضيًا حتى عند إنشاء مستخدم تشغيلي؛ يجب مراجعة دلالة الحقل وخياراته قبل الاعتماد.

### ج. فجوات التغطية الاختبارية

- اختبارات إدارة الوصول الحالية تغطي اشتراط صلاحية المسار، عدم إسناد مجموعة تلقائيًا، منع منح صلاحيات لا يملكها المنفذ، حماية المجموعة الإدارية، وبعض حالات الإسناد والتدقيق.
- اختبارات الهيكل التشغيلي تغطي عينة من نطاق الشركة وإنشاء الفروع وإيقاف الكيانات التابعة.
- لا توجد اختبارات تثبت عزل قائمة المستخدمين أو منع تعديل مستخدم خارج النطاق، ولا اختبارات توريث نطاق الشركة/الفرع عند إسناد نطاق مستخدم، ولا اختبار حماية إعادة تعيين كلمة المرور الذاتية.
- لا توجد اختبارات لحالات المخزون والعهدة الواردة في 7.2؛ لأنها لم تُنفذ بعد. نجاح CI الحالي يثبت نجاح مجموعة الاختبارات الموجودة فقط، ولا يثبت اكتمال هذه الحالات.

### د. ترتيب المعالجة قبل توسيع الصلاحيات

1. إغلاق فجوات نطاق المستخدم المستهدف في جميع عمليات إدارة المستخدمين، مع اختبار الوصول المباشر بمعرف مستخدم خارج النطاق.
2. توحيد دالة/سياسة تفسير نطاق الشركة والفرع والمخزن بحيث تطبق قواعد التوريث نفسها في العرض والإسناد والتحقق.
3. حسم سلوك إعادة تعيين كلمة المرور الذاتية ودلالة `account_type`، ثم إضافة اختبارات تغطي القرار.
4. عند بدء كل مجال تشغيلي، يطبق التفويض بثلاث طبقات على الخادم: صلاحية الفعل + نطاق السجل + حالة المستند، وتضاف اختبارات رفض لكل حالة من 7.2 قبل اعتماد المسار.

**حدود المراجعة:** لم يُعدّل كود أو كتالوج صلاحيات أو Migration في هذه الخطوة، ولم تُشغّل اختبارات محلية جديدة أو تُنشر تغييرات. هذه نتائج قراءة ساكنة للكود والاختبارات الموجودة؛ لا تعتبر فجوات غير المختبرة سلوكًا مختبرًا.
