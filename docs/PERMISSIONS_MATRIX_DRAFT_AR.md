# مصفوفة الصلاحيات — مسودة تجميعية للمراجعة

> الحالة: مسودة تحليلية غير معتمدة نهائيًا. هذه الوثيقة تجمع نتائج الجرد الساكن للكود القديم وقرارات تصميم النظام الجديد. لا تمثل تنفيذًا برمجيًا ولا قائمة مفاتيح نهائية.


## 1.1 منهج التصميم الأكاديمي للنظام الجديد

> **قاعدة حاكمة معتمدة في منهج العمل:** نحن نؤسس نظامًا جديدًا من البداية. النظام القديم مصدر أدلة لفهم المجال واكتشاف الحالات الواقعية والمشكلات والاحتياجات، وليس معيارًا ملزمًا للتصميم أو مرجعًا لنسخ صلاحياته أو شاشاته أو إجراءاته.

يُصمم كل مجال وفق منهج تحليل وتصميم نظم مستقل، بالترتيب التالي:

1. **تحليل أصحاب المصلحة والسياق:** تحديد المستخدمين والجهات والأنظمة المتفاعلة واحتياجات كل طرف.
2. **تحليل المتطلبات:** توثيق المتطلبات الوظيفية وغير الوظيفية، والقيود، والأهداف، ومعايير القبول.
3. **نمذجة العمليات:** تحديد بداية العملية ونهايتها، والأحداث، والقرارات، والاستثناءات، والمسارات البديلة، والمسؤوليات.
4. **نمذجة الحالات:** تعريف حالات الكيانات وانتقالاتها المسموحة وشروط كل انتقال، دون استيراد أرقام أو أسماء الحالات القديمة تلقائيًا.
5. **تحليل الصلاحيات:** اشتقاق صلاحيات دقيقة من العمليات والمهام ومبدأ أقل امتياز، مع فصل الواجبات عند وجود مبرر رقابي أو تشغيلي.
6. **تحليل البيانات:** تحديد الكيانات والعلاقات والقيود والتاريخ التشغيلي وسجل التدقيق ومصدر الحقيقة لكل معلومة.
7. **التصميم المعماري:** تحديد حدود الوحدات والمسؤوليات والتكاملات ومنع ازدواج ملكية البيانات.
8. **التحقق:** مراجعة السيناريوهات الطبيعية والاستثنائية، والتعارضات، وسوء الاستخدام، ومتطلبات الأمن والأداء وقابلية الصيانة.
9. **التتبع والاعتماد:** ربط كل متطلب بعملية وصلاحية وبيانات واختبار، وتسجيل قرار الاعتماد قبل التنفيذ.

### كيفية استخدام النظام القديم

- يُراجع القديم لاكتشاف الوظائف والبيانات والحالات والاستثناءات التي قد لا تظهر في الوصف الأولي.
- كل ملاحظة من القديم تصنف كسلوك قديم مثبت، ولا تتحول تلقائيًا إلى متطلب جديد.
- يُقبل السلوك القديم فقط إذا ثبتت الحاجة إليه واتساقه مع أهداف النظام الجديد والمتطلبات المعتمدة.
- يجوز إعادة تصميم العملية أو دمج الشاشات أو فصلها أو تغيير دورة العمل أو الاستغناء عن سلوك قديم، بشرط توثيق السبب والأثر واعتماد التغيير عند تأثيره على قواعد العمل.
- لا يُفترض أن أسماء الأدوار أو الصلاحيات أو الجداول أو الحالات القديمة تمثل أفضل ممارسة.
- المرجع النهائي هو المتطلبات والقرارات المعتمدة للنظام الجديد، لا مجرد التطابق مع القديم.

### مبادئ هندسية حاكمة

- مبدأ أقل امتياز (Least Privilege).
- الفصل بين المهام (Separation of Duties) بحسب المخاطر، دون فرض فصل شكلي غير مبرر.
- الرفض الافتراضي عند غياب التفويض (Deny by Default).
- التحقق من الصلاحية والنطاق على الخادم في كل عملية.
- فصل هوية المستخدم ونوع الحساب عن صلاحياته الإدارية.
- فصل صلاحية الوصول إلى الوظيفة عن نطاق السجلات التي يجوز الوصول إليها.
- قابلية التدقيق والتتبع وعدم محو التاريخ التشغيلي أو المالي.
- البساطة والاتساق وتقليل التكرار، مع عدم التضحية بوضوح المسؤوليات.

## 1. المبادئ الحاكمة

1. يظل نموذج **مجموعات الصلاحيات** هو طريقة إسناد الصلاحيات للمستخدمين، مع إمكانية تخصيص كل مجموعة من مدير النظام.
2. المسمى الوظيفي أو نوع الحساب لا يمنح صلاحيات إدارية تلقائيًا. نوع الحساب (إداري، تاجر، مسوق، وسيط، مندوب، وغيرها) مستقل عن مجموعة الصلاحيات.
3. نفصل بين مشاهدة الشاشة، ومشاهدة السجل، وتنفيذ الإجراء، واعتماد الإجراء، والترحيل/التنفيذ النهائي.
4. الصلاحية لا تكفي وحدها: يجب التحقق من حالة السجل، وصحة انتقال الحالة، والعلاقات، ونطاق الوصول.
5. إخفاء زر أو رابط ليس حماية؛ التفويض يتم على الخادم في كل عملية.
6. لا تُستخدم معرفات الشركة أو الفرع أو المخزن الواردة من المتصفح دون التحقق من نطاق المستخدم والعلاقات.
7. الصلاحيات الحساسة تسجل في سجل تدقيق، مع دعم فصل المهام عندما تفرضه سياسة العمل.
8. لا ننقل أخطاء التنفيذ القديم، ولا ننسخ تخزين PHP serialized؛ تستخدم مفاتيح ثابتة وعلاقات منظمة.

## 2. قاموس الأفعال المقترح

| الفعل | المقصود |
|---|---|
| View | مشاهدة القوائم والبيانات |
| ViewDetails | مشاهدة تفاصيل سجل محدد |
| Create | إنشاء سجل أو مستند |
| Update | تعديل بيانات أو مستند قبل/وفق ضوابط حالته |
| Cancel | إلغاء منطقي أو تحويل لحالة ملغاة، وليس حذفًا تاريخيًا |
| Delete | حذف فعلي محدود للبيانات المرجعية غير المستخدمة فقط |
| Execute | تنفيذ إجراء تشغيلي مثل الصرف أو الاستلام أو التحويل |
| Submit | إرسال للمراجعة أو الاعتماد |
| Review | مراجعة البيانات والتحقق منها |
| Approve | اعتماد قرار أو نتيجة ضمن اختصاص الدور |
| Reject | رفض مع سبب |
| ReturnForCorrection | إعادة المستند بالكامل للتصحيح مع سبب إلزامي |
| Post | ترحيل أثر مالي/مخزني نهائي |
| Settle | تسوية عهدة أو رصيد أو فرق |

ليست كل الأفعال مطلوبة في كل وحدة؛ يتم اختيار الأفعال المناسبة لطبيعة كل عملية.

## 3. مصفوفة الوحدات والإجراءات الأولية

الرموز:
- **م** مشاهدة، **ت** إنشاء، **ع** تعديل، **ل** إلغاء/تعطيل، **ن** تنفيذ، **ر** مراجعة، **ا** اعتماد، **ح** ترحيل، **س** تسوية/مطابقة، **ض** إعدادات.
- العلامة «مستقل» تعني أن الإجراء يجب أن يكون مفتاحًا منفصلًا، لا أنه دور ثابت أو مستخدم بعينه.
- كل صف أدناه يتطلب تطبيق نطاق البيانات المناسب، ما لم يذكر خلاف ذلك.

| الوحدة | الإجراءات التي ينبغي فصلها | ملاحظات التفويض |
|---|---|---|
| لوحة التحكم | مشاهدة المؤشرات، تصدير التقارير | كل مؤشر يخضع لنطاق بياناته وصلاحية مصدره |
| المستخدمون | مشاهدة، إنشاء، تعديل، تفعيل/تعطيل، إعادة تعيين كلمة المرور، إسناد مجموعة، إدارة أنواع الحسابات | منع تصعيد الامتيازات؛ لا يسند المستخدم صلاحيات تتجاوز ما يملكه |
| مجموعات الصلاحيات | مشاهدة المجموعات والمصفوفة، إنشاء، تعديل، تعطيل/حذف آمن، إسناد للمستخدمين | سجل تغييرات؛ حماية المجموعة المرتبطة بمستخدمين |
| العملاء | مشاهدة القائمة والتفاصيل، إنشاء، تعديل الملف، إدارة العناوين والهواتف، تعطيل | نطاق ملكية/شريك عند وجود مسوق أو وسيط؛ لا تخلط إدارة العميل بإنشاء طلب له |
| الموردون | مشاهدة، إنشاء، تعديل الملف، إدارة العناوين والهواتف، تعطيل | منفصل عن صلاحيات الشراء والاستلام والصرف المالي |
| المؤسسة | مشاهدة بيانات المؤسسة، تعديل بياناتها | صلاحية مستقلة عن صلاحية مشاهدة بيانات مالية |
| الفروع | مشاهدة، إنشاء، تعديل، تعطيل | التحقق من المؤسسة والمدينة ونطاق المستخدم |
| المخازن | مشاهدة، إنشاء، تعديل، تعطيل، إدارة أنواع/خصائص المخازن | التحقق من الفرع ونوع المخزن؛ لا حذف تاريخيًا عند وجود حركات |
| البيانات الجغرافية | إدارة الدول، المحافظات، المدن | صلاحيات إدارة مستقلة؛ السماح بالاستخدام المرجعي في النماذج لا يمنح صلاحية الإدارة |
| مناطق الشحن المحلي | مشاهدة، إنشاء، تعديل، تعطيل، إدارة الأسعار والمدد والربط الجغرافي | تعديل السياسة لا يغير المستندات التاريخية بأثر رجعي |
| إعدادات النظام | مشاهدة وتعديل إعدادات كل مجال، مراجعة التغييرات الحساسة | لا توجد صلاحية عامة واحدة لكل الإعدادات؛ بعض التغييرات قد تحتاج اعتمادًا |
| أوامر البيع | مشاهدة القوائم والتفاصيل، إنشاء، تعديل، إلغاء، تغيير الحالة، إرسال للمراجعة، اعتماد، إعادة للتصحيح | تحقق انتقال الحالة؛ اعتماد الأمر بعد التعديل وفق دورة العمل |
| تأكيد وفرز أوامر البيع | مشاهدة قائمة العمل، مراجعة، تعديل ضمن المرحلة، تثبيت/إرجاع | استثناء الطلب الحالي من احتساب التوافر في منظور الشاشة لا يفك حجزه فعليًا |
| التجهيز للشحن | مشاهدة، بدء التجهيز، تثبيت التجهيز، إلغاء/فك تثبيت التجهيز، إعادة للمرحلة السابقة | فصل التثبيت عن الصرف الفعلي للمندوب/شركة الشحن |
| الصرف وعهدة الشحن | مشاهدة العهدة، إنشاء صرف، تنفيذ الصرف، استرداد الأمر، إبقاء المنتجات بالعهدة أو إعادتها للمخزن | صلاحيات صرف مخزني وإدارة عهدة ونطاق مخزن/جهة عهدة |

| استلام المرتجعات من الشحن | مراجعة وتصحيح نتيجة التوصيل، استلام كامل بإذن واحد، عكس التسوية قبل الإغلاق المالي | لا استلام جزئي ولا إذن ثانٍ؛ العكس يعيد المنتجات للمندوب بحركة موثقة |
| تصحيح العهدة | مراجعة وتصحيح نتيجة التسليم، عكس التسوية المخزنية قبل الإغلاق المالي، إعادة الأمر للمراجعة | العكس يعيد المنتجات للمندوب ويتيح التصحيح وإعادة التسوية؛ سبب ومراجع إلزامية |

| المشتريات | مشاهدة أوامر الشراء، إنشاء، تعديل، إرسال/اعتماد أمر الشراء، إلغاء | اعتماد الشراء منفصل عن استلامه الفعلي |

| الخزائن والبنوك | مشاهدة، إدارة التعريفات، تسجيل قبض، تسجيل صرف، اعتماد سند، ترحيل، تسوية | صلاحيات مستقلة حسب الخزينة/الحساب والنطاق |

| شركة الشحن الخارجية | تسجيل كشف COD، مطابقة الشحنات، تسجيل الخصومات والرسوم، اعتماد المطابقة، إثبات التوريد الفعلي، تسوية الفروق | الكشف لا يثبت قبض الشركة؛ دعم التوريد لكل شحنة أو دوري |
| المرتجعات والاستبدال | إنشاء طلب مرتجع/استبدال، تسجيل السبب لكل منتج، فحص، اعتماد نتيجة الفحص، اعتماد رد المبلغ، تنفيذ الصرف | المستحق المالي للعميل المسجل؛ منشئ الطلب لا يصرف لمجرد تحديده وسيلة الرد |

| سجل التدقيق | مشاهدة السجلات، تصدير، مراجعة أحداث حساسة | قراءة مقيدة؛ لا تعديل أو حذف لسجل التدقيق |
| التكاملات والمهام الآلية | مشاهدة الحالة والسجلات، تشغيل/إعادة محاولة مهمة، إدارة إعداد التكامل | صلاحيات منفصلة؛ لا تمنح صلاحية تعديل البيانات التشغيلية الناتجة |

## 4. نطاق الوصول للبيانات

النطاق ليس فعلًا واحدًا، بل قيد يطبق مع كل صلاحية مشاهدة أو كتابة أو اعتماد.

| بُعد النطاق | الاستخدام |
|---|---|
| الشركة | شركة واحدة أو الشركات المصرح بها أو جميع الشركات |
| الفرع | فرع واحد أو مجموعة فروع أو جميع الفروع المصرح بها |
| المخزن | مخزن واحد أو مجموعة مخازن أو جميع المخازن المصرح بها |
| الشريك/المالك | العملاء والطلبات التابعة للمسوق/الوسيط/الحساب المسموح |
| صاحب العهدة | المندوب الداخلي أو شركة الشحن الخارجية المرتبطة بالعهدة |
| الحساب/الخزينة | الحسابات والخزائن المصرح بها للمستخدم |
| السجل نفسه | منع الوصول لسجل خارج النطاق حتى لو عرف المستخدم رقمه |

قواعد مقترحة:
- النطاق الفعلي هو تقاطع صلاحية الفعل مع نطاق المستخدم وعلاقات السجل.
- لا يسمح بتوسيع نطاق المستخدم من خلال إرسال معرف بديل في الطلب.
- صلاحية «كل الشركات/الفروع/المخازن» يجب أن تكون صريحة ومحددة، ولا تستنتج من الدور.
- التحقق يتم على الخادم في القراءة والكتابة والتصدير والاعتماد.

## 5. فصل المهام والاعتمادات

هذه ضوابط مرتبطة بالعملية وليست أدوارًا عامة ثابتة:

- أمين المخزن مسؤول عن الاستلام المخزني الكامل، ويجوز له تنفيذ عكس التسوية المخزنية قبل الإغلاق المالي وفق الضوابط المعتمدة.
- يجوز للمسؤول عن التحصيل المالي أيضًا تنفيذ عكس التسوية المخزنية قبل الإغلاق المالي؛ ويظل تنفيذ العكس مقيدًا بتوافر كامل الكمية الحرة، وعدم المساس بحجوزات أو كميات أوامر أخرى، وحفظ السبب والأثر التاريخي.
- المسؤول المالي يعتمد الأثر المالي والتحميل والتسويات المالية.
- المسؤول المالي يستطيع إعادة أمر العهدة بالكامل للمسؤول المخزني للتصحيح بسبب إلزامي؛ وبعد التصحيح يعود الأمر للمراجعة المالية.
- يمكن لمستخدم واحد الجمع بين صلاحيات المسؤول المخزني وأمين المخزن إذا أسندت له المجموعتان/الصلاحيات؛ لا نفرض فصلًا وظيفيًا مطلقًا.
- إعدادات اعتماد رد المبالغ تدعم مستوى واحدًا أو عدة مستويات، وحدود مبالغ، وتحديد الأدوار/المستخدمين، ومنع المنشئ من الاعتماد أو اشتراط اختلاف المعتمدين حسب السياسة.
- لا ينشأ أثر مالي نهائي من إجراء مخزني وحده، ولا تنشأ حركة مخزنية من اعتماد مالي وحده.

## 6. حالات خاصة لا تختزل إلى CRUD

1. **أمر البيع:** تعديل البيانات لا يعني اعتمادها؛ يلزم مسار اعتماد بعد التعديل.
2. **الحجز:** الحجز يبدأ عند إنشاء الطلب، لكن الاحتفاظ به وتأثير الحالة على المتاح تحددهما إعدادات المخزون المحتجز.
3. **عهدة الشحن:** حالة الطلب منفصلة عن حيازة المنتجات؛ استرداد الطلب لا يعني بالضرورة عودة المنتجات للمخزن.
4. **عكس التسوية المخزنية:** إجراء إلزامي عند كل إعادة رسمية للتصحيح بعد اكتمال التسوية وقبل الإغلاق المالي؛ لا يسمح بالتصحيح دون العكس حتى إذا لم تتغير الكميات. ينفذه أمين المخزن أو المسؤول عن التحصيل المالي وفق الصلاحية، ويعيد المنتجات المستلمة إلى جهة التوصيل بحركة صرف مرتبطة بعكس الاستلام، بعد التحقق من توافر كامل الكمية الحرة.
5. **شركة الشحن:** تقرير التوصيل لا ينشئ دخولًا مخزنيًا ولا يثبت قبض الشركة للمبالغ.
6. **المرتجع:** لا يعاد المنتج للمتاح إلا بعد الاستلام الفعلي والفحص والاعتماد.
7. **الإعدادات:** يجب حفظ نسخة السياسة/القيمة التي طبقت على المستند وقت إنشائه أو اعتماده عندما يكون للتغيير أثر تاريخي.

## 7. عناصر لم تحسم بعد

- القائمة النهائية لمفاتيح الصلاحيات الدقيقة وتسمياتها الثابتة.
- هل يتم تعطيل الكيانات المرجعية دائمًا أم يسمح بحذف فعلي في حالات محددة.
- الصلاحيات التفصيلية لكل شاشة إعدادات عامة، بعد اكتمال جردها.
- من يملك اعتماد التغييرات الحساسة في إعدادات المخزون والشحن والحسابات.
- مصفوفة الأدوار الافتراضية المقترحة للمستخدمين الجدد؛ لم تعتمد بعد.
- قواعد التفويض الدقيقة للتاجر والمسوق والوسيط والمندوب والعملاء المسجلين.
- حدود تصدير البيانات الحساسة وسجل التدقيق.
- الصلاحيات النهائية للتكاملات والمهام الآلية.
- تفاصيل مفاتيح إدارة الحسابات والأستاذ العام وفق وثائق المجال المالي على الفرع المرجعي.


## 7.1 قاموس مفاتيح الصلاحيات — اتجاه مبدئي

> وافق المستخدم مبدئيًا على نمط التسمية وفصل الأفعال والاتجاه العام. المفاتيح أدناه مسودة للمراجعة وليست اعتمادًا نهائيًا أو قائمة مكتملة، ولا يبدأ تنفيذها قبل مراجعة كل وحدة واعتماد القاموس.

### نمط التسمية

النمط المقترح: `module.resource.action`

أمثلة: `sales.orders.view`، `sales.orders.create`، `inventory.stock.receive`، ، `custody.stock_settlement.reverse`.

- مفاتيح ثابتة باللغة الإنجليزية، والفعل محدد وواضح.
- المشاهدة والتعديل والتنفيذ والمراجعة والاعتماد والترحيل أفعال مستقلة.
- مجموعات الصلاحيات تجمع المفاتيح؛ ولا يستمد المستخدم صلاحية تلقائيًا من المسمى الوظيفي أو نوع الحساب.
- لا تستخدم أرقام حالات النظام القديم في أسماء المفاتيح؛ الحالات والانتقالات قاموس مستقل.
- المفتاح يخضع أيضًا لنطاق الوصول وحالة السجل وصحة الانتقال وفصل المهام.

### قيود لا تختزل إلى مفتاح صلاحية

- نطاق الشركة والفرع والمخزن والشريك وصاحب العهدة والحساب/الخزينة والسجل يطبق على القراءة والكتابة والاعتماد والتصدير.
- حالة المستند وانتقالاته تتحقق في الخادم.
- فصل المهام يطبق وفق سياسة العملية، مع التحقق من أهلية منفذ عكس التسوية وحالة الإغلاق المالي.
- التصدير مستقل عن المشاهدة، ويخضع لنطاق البيانات وضوابط الحقول الحساسة.
- الإعدادات الحساسة قد تحتاج اعتمادًا إضافيًا؛ من يملك الاعتماد وحدوده ما زال سؤالًا مفتوحًا.

### حالة الموافقة

الموافقة الحالية مبدئية على الاتجاه والنمط والفصل بين الأفعال فقط. لا تعني اعتماد كل مفتاح أو اكتمال القائمة. تراجع المفاتيح مع كل وحدة قبل اعتماد النسخة النهائية. لم يتم إنشاء جداول أو migrations أو Policies أو شاشات، ولم تتغير قاعدة البيانات أو بيئة النشر.


## 8. حالة هذه الوثيقة

- تجمع نتائج جرد ساكن لعدة جولات على المشروع القديم، وقرارات تشغيلية وتصميمية صرح بها المستخدم.
- الصفوف هي مجموعات إجراءات مقترحة وليست اعتمادًا نهائيًا لكل مفتاح.
- لم يتم إنشاء جداول صلاحيات أو migrations أو Policies أو شاشات.
- لم يتم تنفيذ اختبارات تشغيلية أو أمنية.
- نطاق المستخدمين ومجموعات الصلاحيات أعلاه معتمد كبداية تنفيذية، ويجري تنفيذه واختباره على فرع `rebuild-v2`.
- بقية المفاتيح تظل مسودة حتى تحليل واعتماد كل وحدة على حدة.
