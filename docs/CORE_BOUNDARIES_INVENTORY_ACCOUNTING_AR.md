# وثيقة حدود ومسؤوليات نواة المخازن ونواة الحسابات
**المشروع:** Just-M V2  
**الحالة:** وثيقة حدود ومسؤوليات تصميمية مرجعية. المبادئ وحدود الملكية والتكامل معتمدة كاتجاه معماري؛ تفاصيل التكلفة والقيود والأحداث والجداول التي لم تعتمد صراحة تظل مفتوحة. لا تدّعي الوثيقة أن النواتين منفذتان برمجيًا.  
**الفرع:** `rebuild-v2`  
**المرجع المعماري:** `docs/REBUILD_V2_ARCHITECTURE_AR.md`  
**مرجع النظام القديم:** `main`، مع اعتبار وثائقه الحالية خاصة بالمجال المالي/المحاسبي فقط  
**تاريخ الإعداد:** 2026-11-08

---

## 1. الغرض والنطاق

تحدد هذه الوثيقة حدود المسؤولية بين نواتين أساسيتين في النظام الجديد:

1. **Inventory Core — نواة المخازن:** مصدر الحقيقة للكميات والمواقع والحركات والحجوزات والتكلفة المخزنية.
2. **Accounting Core — نواة الحسابات:** مصدر الحقيقة للأثر المالي والأرصدة المحاسبية والقيود والأستاذ العام.

الهدف هو منع ازدواج ملكية البيانات، ومنع أن تقوم وحدة بتعديل بيانات جوهرية تملكها الوحدة الأخرى مباشرة، مع إتاحة التكامل من خلال أحداث وعقود واضحة وقابلة للتدقيق.

هذه الوثيقة لا تصمم كل جداول قاعدة البيانات، ولا تعتمد سياسة تكلفة أو قيودًا محاسبية تفصيلية، ولا تبدأ تنفيذًا برمجيًا. تلك قرارات لاحقة بعد تحليل العمليات واعتمادها.

## 2. المبادئ الحاكمة

1. لكل حقيقة تشغيلية مالك واحد واضح.
2. رصيد المخزون لا يُعدّل يدويًا؛ يتغير نتيجة حركة مخزنية معتمدة.
3. الرصيد المحاسبي لا يُعدّل يدويًا؛ يتغير نتيجة ترحيل قيد أو تسوية معتمدة.
4. لا تنشئ نواة المخازن قيود الأستاذ العام بنفسها، ولا تنشئ نواة الحسابات حركات أو كميات مخزنية.
5. مصدر الحقيقة ليس شاشة أو تقريرًا أو قيمة مخزنة مؤقتًا؛ بل سجل الحركة/القيد المعتمد.
6. العمليات المركبة يجب أن تكون قابلة للتتبع من المستند الأصلي حتى أثرها المخزني والمالي.
7. إعادة إرسال الحدث أو الطلب لا يجوز أن تكرر الأثر (Idempotency).
8. التصحيح يتم بحركة عكسية أو قيد عكسي موثق، وليس بمحو التاريخ.
9. يجب حفظ المستخدم والوقت والسبب والمصدر والمستند المرجعي لكل حركة مؤثرة.
10. لا يُسمح بترحيل مالي أو مخزني بناءً على حدث غير مكتمل أو غير معتمد.

## 3. نواة المخازن — Inventory Core

### 3.1 المسؤوليات

- تعريف المخازن والفروع ومناطق/مواقع التخزين عند الحاجة.
- تعريف وحدات القياس والتحويلات المعتمدة، بالتنسيق مع كتالوج المنتجات.
- إدارة أرصدة الأصناف حسب الصنف والمخزن والموقع وحالة المخزون.
- تسجيل الوارد والصادر والتحويلات والتسويات والجرد.
- إدارة الحجز وفك الحجز وربطه بالمستند المسبب.
- إدارة الاستلام الفعلي والمرتجعات من منظور الكمية والحالة.
- تسجيل تتبع الدفعات/الأرقام التسلسلية/الصلاحية إذا أثبت التحليل الحاجة إليها.
- حساب أو حفظ قيمة/تكلفة الحركة وفق سياسة تقييم مخزون تعتمد لاحقًا.
- توفير سجل حركة كامل وقراءة رصيد لحظي/تاريخي قابل للمطابقة.

### 3.2 ما لا تملكه نواة المخازن

- دليل الحسابات أو أرصدة الأستاذ العام.
- أرصدة العملاء والموردين المالية.
- الخزائن والبنوك وسندات القبض والصرف.
- تحديد الحسابات المدينة والدائنة أو إنشاء قيد GL.
- اعتماد سياسة الاعتراف بالإيراد أو المصروف أو العمولة.

### 3.3 حقائق وكيانات مفاهيمية

هذه قائمة مفاهيمية وليست أسماء جداول نهائية:

- Warehouse / Store
- Storage Location (إن لزم)
- Stock Item / Product Variant
- Unit of Measure / Conversion
- Stock Balance (قراءة مشتقة أو ملخص مضبوط)
- Stock Movement / Movement Line
- Reservation / Reservation Line
- Stock Count / Count Line
- Stock Transfer
- Goods Receipt
- Goods Issue
- Inventory Adjustment
- Return Receipt

### 3.4 دورة الحركة المخزنية العامة

1. ينشأ طلب أو مستند مصدر من الوحدة المختصة (مثل شراء أو بيع أو تحويل أو مرتجع).
2. تتحقق نواة المخازن من الصنف والمخزن والوحدة والكمية والحالة والصلاحيات.
3. عند الحاجة، تنشئ حجزًا مستقلًا عن الصرف الفعلي.
4. عند تحقق الحدث الفعلي، تعتمد الحركة المخزنية وتسجل تفاصيلها ومصدرها.
5. يحدث ملخص الرصيد داخل معاملة قاعدة بيانات متسقة مع سجل الحركة.
6. تصدر النواة حدثًا موثوقًا عن الحركة المعتمدة، متضمنًا مرجعها وقيمها اللازمة للتكامل.
7. لا يُسمح بتعديل الحركة المرحلة؛ التصحيح بحركة عكسية أو تسوية جديدة وفق الصلاحيات.

**تمييز إلزامي:** الحجز ليس صرفًا، وتجهيز الطلب ليس تسليمًا، وخروج البضاعة من المخزن ليس بالضرورة إثباتًا لتسليمها للعميل. تعريف كل حدث وحدوده يعتمد على دورة العمل المعتمدة.

## 4. نواة الحسابات — Accounting Core

### 4.1 المسؤوليات

- إدارة دليل الحسابات وشجرته وخصائص الحسابات.
- إدارة الفترات والسنوات المالية وحالات فتح/إغلاق الفترة.
- إنشاء واعتماد وترحيل القيود اليومية.
- ضمان توازن القيد والتحقق من صلاحية الحسابات ومراكز التكلفة.
- إدارة الأستاذ العام والأرصدة المحاسبية والتقارير.
- إدارة المستندات المالية مثل القبض والصرف والتسويات ضمن حالات الاستخدام المعتمدة.
- ربط القيود بمصادرها التشغيلية ومنع تكرار الترحيل.
- إدارة عكس القيود وإعادة الترحيل وفق ضوابط تدقيق.
- توفير واجهات تكامل للأحداث التي تستلزم أثرًا ماليًا.

### 4.2 ما لا تملكه نواة الحسابات

- الكمية الفعلية المتاحة في المخزن.
- حجز الأصناف أو صرفها أو استلامها.
- اعتماد أن التسليم أو الاستلام المخزني قد حدث فعليًا.
- تعديل رصيد صنف أو موقع تخزين.
- تقرير صلاحية منتج للصرف أو تحديد مكانه الفعلي.

### 4.3 حقائق وكيانات مفاهيمية

هذه قائمة مفاهيمية وليست أسماء جداول نهائية:

- Account / Account Group
- Journal Entry / Journal Line
- Fiscal Period / Fiscal Year
- Cost Center
- Financial Document
- Posting Rule / Posting Profile
- Source Event / Posting Reference
- Reversal Entry
- General Ledger Balance (ملخص مشتق من القيود المرحلة)

### 4.4 دورة الترحيل المالي العامة

1. تستقبل نواة الحسابات حدثًا أو طلب ترحيل من مصدر موثوق.
2. تتحقق من هوية الحدث وعدم سبق معالجته، ومن اكتمال بياناته.
3. تطبق قاعدة الترحيل المعتمدة للحالة، لا قاعدة ضمنية داخل الشاشة.
4. تتحقق من الفترة والحسابات والأبعاد المطلوبة وتوازن القيد.
5. تنشئ القيد وترحله وفق سياسة الاعتماد.
6. تحفظ مرجع المصدر ومفتاح منع التكرار وسجل التدقيق.
7. تعيد نتيجة واضحة إلى مصدر الحدث أو توفر حالة معالجة قابلة للاستعلام.
8. التصحيح يكون بقيد عكسي/تسوية، مع الاحتفاظ بالقيد الأصلي.

لا يتم استنتاج قيد محاسبي من اسم حركة مخزنية وحده؛ يجب اعتماد مصفوفة أحداث/قيود تحدد متى ينشأ الأثر المالي ومتى لا ينشأ.

## 5. حدود البيانات وملكية الحقيقة

| المعلومة | مالك الحقيقة | ملاحظات |
|---|---|---|
| الكمية الفعلية حسب المخزن والصنف | المخازن | لا تعدل من الحسابات |
| الحجوزات والكميات المتاحة | المخازن | يجب تعريف أثر الحجوزات بدقة |
| سجل حركات المخزون | المخازن | سجل غير قابل للمحو بعد الاعتماد |
| قيمة/تكلفة المخزون | المخازن من ناحية التقييم | سياسة التقييم وطريقة تمرير القيمة للحسابات تحتاج اعتمادًا |
| دليل الحسابات | الحسابات | لا تملكه وحدات التشغيل |
| القيود والأستاذ العام | الحسابات | المصدر الوحيد للحقيقة المالية |
| أرصدة العملاء/الموردين المحاسبية | الحسابات | مع احتمال وجود بيانات تشغيلية مستقلة للطرف |
| حالة مستند البيع/الشراء/المرتجع | الوحدة المالكة للمستند | لا تستبدل بحالة مخزنية أو قيد محاسبي |
| المستخدم والصلاحيات | الهوية والصلاحيات | النواتان تطلبان التفويض ولا تعيدان تعريفه |

## 6. التكامل بين النواتين

### 6.1 القاعدة

التكامل يكون عبر **أحداث أعمال موثقة وعقود بيانات محددة**. لا تستدعي نواة المخازن وظائف داخلية في الحسابات لتعديل الأرصدة، ولا تستدعي الحسابات وظائف داخلية في المخازن لتعديل الكميات.

### 6.2 أمثلة أحداث مرشحة

الأسماء التالية وصفية مبدئية وليست أسماء أحداث نهائية:

- `InventoryReceiptPosted`
- `InventoryIssuePosted`
- `InventoryTransferPosted`
- `InventoryAdjustmentPosted`
- `InventoryReturnReceived`
- `InventoryCostFinalized`

ليس كل حدث مخزني بالضرورة حدثًا ماليًا. تُعتمد مصفوفة توضح لكل حدث: هل له أثر مالي؟ متى؟ ما القيمة؟ ما الحسابات؟ وما شروط الترحيل؟

### 6.3 الحد الأدنى لعقد الحدث

- معرف فريد للحدث.
- نوع الحدث وإصداره.
- وقت وقوع الحدث ووقت تسجيله.
- معرف المستند المصدر ونوعه.
- معرف الحركة المخزنية المعتمدة.
- الفرع والمخزن عند انطباقهما.
- تفاصيل الصنف والوحدة والكمية.
- قيمة/تكلفة الحركة والعملة عند انطباقهما وبعد اعتماد سياسة التقييم.
- المستخدم أو النظام الذي نفذ العملية.
- مفتاح منع التكرار.
- بيانات تفسيرية/سبب الحركة دون وضع أسرار أو بيانات غير لازمة.

### 6.4 ضمان تسليم الأحداث

نحتاج نمطًا موثوقًا مثل Transactional Outbox أو بديلًا مكافئًا: تحفظ الحركة المخزنية ورسالة الحدث في معاملة واحدة، ثم تتم محاولة تسليم الحدث وإعادة المحاولة عند الفشل. يجب أن تكون معالجة الحسابات Idempotent حتى لا يتكرر القيد عند إعادة التسليم.

اختيار التقنية والتنفيذ التفصيلي مؤجلان إلى تصميم البنية وقاعدة البيانات.

## 7. أمثلة توضح الفصل

| العملية | مسؤولية المخازن | مسؤولية الحسابات |
|---|---|---|
| استلام بضاعة | إثبات الكميات والحالة والمخزن | تحديد وجود قيد ومتى وقيمته وفق مستند المصدر والسياسة المعتمدة |
| صرف بضاعة | إثبات الصرف الفعلي وتكلفته | تسجيل أثر التكلفة إذا كانت العملية تستلزم ذلك |
| تحويل بين مخزنين | إخراج من المصدر وإدخال للوجهة وربط الحركتين | لا يفترض قيد مالي تلقائي؛ يحدد وفق السياسة |
| جرد وتسوية كمية | إثبات فرق الجرد واعتماد التسوية | تقييم الأثر المالي وترحيله عند انطباقه |
| استلام مرتجع عميل | إثبات الاستلام والكمية والحالة | لا ينفذ ردًا ماليًا تلقائيًا لمجرد وجود طلب مرتجع؛ يطبق قواعد المرتجع المعتمدة |
| حجز طلب بيع | حجز كمية متاحة | لا ينشأ قيد GL لمجرد الحجز ما لم تعتمد قاعدة صريحة بخلاف ذلك |

الأمثلة توضح الحدود فقط، ولا تحسم القيود أو السياسات المحاسبية.

## 8. الضوابط المشتركة

- كل حركة/قيد له رقم مرجعي فريد.
- استخدام معاملات قاعدة البيانات في كل عملية متعددة الخطوات داخل النواة.
- مفاتيح فريدة تمنع تكرار اعتماد الحركة أو ترحيل الحدث.
- لا يسمح بتعديل مستند مرحل دون مسار تصحيح معتمد.
- فصل وقت إنشاء المستند عن وقت اعتماده/ترحيله.
- سجل تدقيق يسجل من فعل ماذا ومتى ولماذا.
- استخدام أنواع رقمية دقيقة للكميات والقيم، وتجنب FLOAT للمبالغ.
- تحديد قواعد التقريب والدقة ووحدات القياس.
- دعم صلاحيات منفصلة للإنشاء والمراجعة والاعتماد والترحيل والعكس.
- التقارير تقرأ من مصادر الحقيقة أو إسقاطات مشتقة قابلة لإعادة البناء والمطابقة.

## 8.1 مصفوفة الأحداث التشغيلية والأثر المخزني والمحاسبي — إصدار التحليل الأول

**الحالة:** هذه المصفوفة تجمع القواعد المعتمدة في وثائق Just-M ونتائج مراجعة المجال المالي على `main`. هي أساس تحليل وتصميم وليست اعتمادًا لأرقام حسابات أو دليل حسابات نهائي أو أسماء جداول أو ترحيل برمجي. كل بند موضح بحالته حتى لا يتحول السلوك القديم إلى قرار جديد دون اعتماد.

| الحدث | الأثر المخزني المعتمد/المطلوب | الأثر المحاسبي | شرط التوقيت والضبط | حالة المعرفة |
|---|---|---|---|---|
| إنشاء أمر البيع والحجز | حجز الكمية المتاحة للطلب؛ لا خروج فعلي ولا تغيير في الكمية الفعلية | لا قيد أستاذ عام لمجرد إنشاء الطلب أو الحجز | الحجز مرتبط بالطلب والصنف والمخزن، ويُفك أو يُستهلك بالصرف وفق انتقال الحالة | قاعدة معمارية معتمدة؛ توقيت بدء الحجز التفصيلي يحتاج استكمال دورة الطلب |
| تجهيز الطلب | إثبات التجهيز كمرحلة مستقلة؛ لا يعد تسليمًا ولا صرفًا نهائيًا بذاته | لا قيد لمجرد التجهيز | لا تخلط حالة التجهيز مع حالة الصرف أو التسليم | قاعدة معتمدة |
| صرف الطلب إلى مندوب داخلي أو شركة شحن | خروج من عهدة المخزن ودخول في عهدة جهة التوصيل؛ لا يعد بيعًا ولا استلامًا من العميل | لا يُنشأ قيد تكلفة مبيعات لمجرد نقل الحيازة؛ يظل المخزون أصلًا مع تتبع موقع/حائز المخزون | يجب توثيق جهة الحيازة والكمية والمستند. لا يثبت تقرير شركة الشحن استلام المخزن أو النقدية | قاعدة عمل معتمدة؛ تفصيل حسابات مراقبة المخزون حسب الحيازة مفتوح |

### قواعد عامة مستخلصة من المصفوفة

1. **الحجز والتجهيز ونقل الحيازة ليست بيعًا:** لا تُثبت إيرادًا أو تكلفة مبيعات لمجرد حدوثها.
2. **التسليم الفعلي هو أساس كمية البيع:** لا تُثبت مبيعات أو تكلفة مبيعات لكمية لم يثبت تسليمها، ولا تُدخل المرتجعات إلى رصيد المخزن قبل الاستلام الفعلي.
3. **التحصيل حدث مستقل عن البيع:** إثبات المديونية والتحصيل وتوريد المندوب/شركة الشحن أحداث منفصلة، ولكل منها مستند وقيد/تخصيص مستقل.
4. **المخزون والأستاذ العام مالكان منفصلان:** نواة المخزون تسجل الحركة والتكلفة، ونواة الحسابات فقط ترحل القيد؛ لا تنشئ أي نواة أثر الأخرى مباشرة.
5. **منع التكرار والتصحيح:** كل حدث مصدره فريد، وكل ترحيل/تخصيص قابل للتتبع والعكس دون حذف الأصل.
6. **لا تخمين في الحسابات:** لا تُكتب أرقام حسابات ولا تنشأ حسابات تلقائيًا قبل اعتماد دليل الحسابات وربط الإعدادات.
7. **الاستثناءات المفتوحة لا توقف توثيق المعتمد:** تسجل الفجوة وتظل معزولة، ولا تعطل بناء الأجزاء التي حُسمت.

### ما لا تحسمه هذه المصفوفة بعد

- الحساب المدين المناسب لبيع جهة التوصيل: هل يظل العميل أم يتحول إلى حساب مراقبة جهة التوصيل عند تحقق شروط معينة؟
- طريقة إثبات قيمة المخزون أثناء وجوده في عهدة المندوب/شركة الشحن، وعلاقة ذلك بحسابات المخزون الفرعية.
- سياسة تقييم المخزون المعتمدة تفصيليًا، وتوقيت تثبيت تكلفة الصرف والمرتجع والجرد.
- قيد إثبات شراء المخزون وتوقيت فصل الفاتورة عن الاستلام.
- حسابات رسوم الشحن للعميل ورسوم شركة الشحن، وتوقيت الاعتراف بكل منهما.
- حسابات فرق الجرد والتالف والفروق المقبولة.
- تفاصيل القيد والتخصيص والعكس في إلغاء الطلب قبل التسليم.

## 8.2 مطابقة المصفوفة مع تنفيذ المخزون القديم — أدلة لا تُنقل تلقائيًا

نتائج المراجعة الساكنة في `LEGACY_INVENTORY_AUDIT_AR.md` تؤكد النقاط التالية، مع الالتزام بأن كود `main` دليل على السلوك القديم وليس مواصفة تلقائية للنظام الجديد:

1. **صرف البيع المباشر والشحن:** `InventoryManager::processSalesOrder()` يسجل حركات `SALES` و`SHIPPING` كـ `OUT`، بينما صرف الشحن ينشئ عهدة جهة التوصيل في مسار منفصل. يجب أن يظل إثبات التسليم/البيع مستقلًا عن حركة الصرف.
2. **مرتجعات محاولة التوصيل:** التنفيذ القديم يحسب كمية `RETURN_SHIPP` من `QTY - DELIVERED_QTY`. هذا لا يثبت أن الكمية وصلت فعليًا للمخزن. **يُرفض نقل هذه المعادلة ككمية وارد في النظام الجديد**؛ الكمية الواردة هي ما سجله أمين المخزن واستلمه فعليًا في إذن الاستلام الواحد.
3. **مرتجع ما بعد البيع:** الحركة القديمة `RETURN_SALES` تعتمد `RETURNED_QTY`. يظل هذا المسار منفصلًا عن رجوع شحنة لم تسلم للعميل، وعن رد الأموال.
4. **استرداد الأمر المجمّد:** توجد دلالة قديمة على إمكانية إعادة الأمر إداريًا دون إعادة المنتجات؛ لذلك لا يجوز اعتبار فك/إغلاق العهدة دليلًا على رجوع المخزون. القاعدة الجديدة تتطلب استلام المنتجات فعليًا قبل إضافتها للمخزن.
5. **المشتريات:** الكود القديم يدعم الاستلام الجزئي عبر `QTY_SUPPLIED`، ومرتجع المورد عبر `QTY_RETURN` مع فحص الكمية المستلمة والمرتجعات السابقة ورصيد المخزن. هذا يثبت الحاجة إلى فصل أمر الشراء عن دفعات الاستلام وفاتورة المورد ومرتجع المورد وسداد المورد، ولا يحسم القيود المالية.
6. **التحويل الداخلي:** التنفيذ القديم ينشئ حركة `OUT` للمخزن المصدر وحركة `IN` للمخزن المستلم ضمن مسار واحد؛ لم يظهر مسار مخزون «بالطريق». لا ننقل هذا القيد قبل اعتماد ما إذا كان النظام الجديد يحتاج استلامًا منفصلًا.
7. **الجرد:** الكود القديم يقفل المخزن أثناء الجرد، ويقارن الكمية الفعلية بالرصيد، ثم يسجل فرقًا موجبًا `IN` أو سالبًا `OUT`. وجود القفل لا يثبت وجود اعتماد مستقل للفرق أو سياسة محاسبية له.
8. **الهالك:** ظهر خلل محتمل في دالة `processScrap()` القديمة في نوع الحركة والمتغير المستخدم؛ لا يعتمد هذا التنفيذ ولا يُنسخ. يلزم تصميم حركة هالك صريحة عند اعتماد سياسة الهالك.
9. **التكلفة:** وجود `CODE_COST_PRICE` في كتالوج المنتج أو `COST_PRICE` على بند أمر البيع لا يكفي وحده لإثبات سياسة تقييم المخزون أو تكلفة الصرف التاريخية. لا يجوز استبدال تكلفة حركة قديمة بسعر تكلفة حالي أو افتراض طريقة FIFO/متوسط دون اعتماد.

هذه المطابقة تدعم قرارات الفصل بين الحيازة والحركة والبيع والاستلام، لكنها لا تعتمد جداول أو أسماء حركات جديدة ولا تُعد اختبارًا تشغيليًا على قاعدة بيانات قديمة.

## 8.3 قاموس بيانات مفاهيمي أولي لنواة المخزون وربط الأستاذ العام

| سطور الحجز (Reservation Lines) | تحديد الصنف والكمية المحجوزة | مرجع بند الطلب، الصنف، الوحدة، الكمية، الكمية المستهلكة/المحررة | لا يُسمح باستهلاك أو تحرير أكثر من المتبقي؛ الحجز مرتبط بمصدر محدد |
| مستند عهدة جهة التوصيل (Delivery Custody) | إثبات انتقال حيازة المنتجات من المخزن إلى المندوب/شركة الشحن | جهة التوصيل، الأمر، المخزن المصدر، حالة العهدة، وتواريخ الصرف/التسوية | المندوب الداخلي وشركة الشحن نوعان مستقلان؛ لا تُسجل شركة الشحن كعمولة مندوب |
| سطور العهدة | تتبع الصنف والكمية لدى جهة التوصيل | الصنف، كمية الصرف، كمية التسليم المثبتة، كمية المرتجع الفعلي، مرجع حركة الصرف والاستلام | نتيجة التوصيل لا تعني استلام المرتجع؛ لا تضاف للمخزون إلا الكمية التي استلمها أمين المخزن |
| مستند استلام توريد (Goods Receipt) | إثبات وصول بضاعة المورد | مرجع أمر الشراء والمورد والمخزن وتاريخ الاستلام والحالة | يدعم تعدد دفعات الاستلام حيثما اعتمدت سياسة الشراء؛ يفصل عن فاتورة المورد والدفع |
| سطور استلام التوريد | الكميات المستلمة لكل صنف | مرجع بند أمر الشراء، الصنف، الوحدة، الكمية المقبولة والمرفوضة إن اعتمدت | مجموع الاستلام لا يتجاوز المتبقي من أمر الشراء؛ كل دفعة لها حركة وارد مستقلة |
| مستند استلام مرتجع (Return Receipt) | إثبات رجوع بضاعة من جهة التوصيل أو العميل | نوع المرتجع، الأمر، الجهة الحائزة، المخزن المستلم، المنفذ، وتاريخ الاستلام | مساران منفصلان: مرتجع محاولة توصيل، ومرتجع بعد البيع؛ الأول إذن واحد بكامل المرتجع الفعلي لكل أمر |
| سطور المرتجع | تحديد ما وصل فعليًا من كل صنف | الصنف، الكمية الفعلية المستلمة، الحالة/نتيجة الفحص عند الحاجة، ومرجع سطر الطلب | لا تعتمد كمية متوقعة من نتيجة التوصيل بدل الكمية المستلمة فعليًا |
| مستند تحويل مخزني (Stock Transfer) | نقل ملكية الحيازة بين مخزنين | المخزن المصدر والوجهة، الحالة، المنشئ، ومرجع واحد يربط طرفي التحويل | هل توجد حالة «بالطريق» أم تحويل فوري؟ مفتوح؛ لا تعتمد طريقة النظام القديم تلقائيًا |
| مستند جرد (Stock Count) | تسجيل الكمية الفعلية ومراجعتها | المخزن، تاريخ القطع، المنفذ/المراجع، الحالة، وسبب الفروقات | القفل يمنع تعارض الحركات؛ اعتماد فرق الجرد وصلاحياته ما زالا مطلوبين |
| سطور الجرد والتسوية | مقارنة الفعلي بدفتر المخزون | الصنف، الرصيد الدفتري، الفعلي، الفرق، وحركة التسوية الناتجة | لا تعديل رصيد مباشر؛ كل فرق ينتج حركة مخزنية موثقة |
| حدث تكامل محاسبي (Accounting Source Event) | تسليم حدث تشغيلي لنواة الحسابات | نوع الحدث وإصداره، مصدره الفريد، الحركة/المستند، القيمة والتكلفة المعتمدة، حالة المعالجة | Outbox أو آلية مكافئة؛ إعادة المحاولة لا تكرر القيد |
| قيد الأستاذ العام (Journal Entry) | تسجيل الأثر المالي للحدث | تاريخ القيد، الفرع، المصدر، الحالة، وسطور الحسابات المدينة/الدائنة والأطراف | ملكية نواة الحسابات فقط؛ توازن القيد، منع التكرار، وعدم تعديل المرحل |
| تخصيصات الأستاذ (Ledger Allocations) | ربط التحصيل/الائتمان بمديونية أو استحقاق | سطر مدين وسطر دائن والطرف والمبلغ المخصص | لا تنشئ قيدًا؛ تسمح بالجزئي وتحتفظ بتاريخ العكس |

### العلاقات الأساسية المقترحة

1. الشركة ← الفروع ← المخازن؛ هذا التسلسل موجود بالفعل في بيانات الهيكل على `rebuild-v2`.
2. الصنف الواحد له عدة حركات وسطور حجز وعهدة واستلام وجرد؛ لا يخزن الرصيد باعتباره سجلًا مستقلًا غير قابل للمطابقة.
3. أمر البيع يملك بنودًا؛ كل بند يمكن أن يرتبط بحجز، ثم حركة صرف، ثم سطر عهدة، ثم نتيجة تسليم، ثم سطر استلام مرتجع إن عاد المنتج.
4. أمر الشراء يملك بنودًا؛ يمكن أن يرتبط بأكثر من مستند استلام، ثم بفاتورة مورد مستقلة، ثم بدفعة/تخصيص مالي.
5. مستند الحركة قد ينتج عنه حدث محاسبي واحد أو أكثر حسب مصفوفة الترحيل؛ لا يُفترض أن كل حركة مخزنية تنتج قيدًا.
6. حدث المصدر يرتبط بقيد الأستاذ عبر مرجع فريد ومفتاح idempotency؛ التخصيصات تربط سطور الأستاذ ولا تستبدلها.
7. مستند العكس يشير إلى المستند الأصلي ويحتفظ بسلسلة الأحداث السابقة؛ لا حذف ولا تحديث صامت.

### ما لا يزال خارج الاعتماد النهائي

- تم اختيار وصف «other» لإعداد تقييم المخزون في النقاش السابق، لكن المقصود التشغيلي لم يُعرّف بعد. تدقيق النظام القديم أثبت تكلفة مرجعية يدوية لكل SKU تُنسخ إلى بند الطلب، وليس FIFO أو متوسطًا مرجحًا؛ يلزم تحديد هل نعتمد هذا مؤقتًا أم سياسة أخرى قبل بناء محرك التكلفة.
- طريقة تمثيل الحيازة لدى جهة التوصيل في الأرصدة المخزنية (موقع مستقل أو سجل عهدة مرتبط بموقع).
- التحويل الفوري مقابل حالة «بالطريق».
- تفاصيل الوحدات والكسور والدفعات/الأرقام التسلسلية وحالات الجودة.
- نقطة الاعتراف المحاسبي في المشتريات وربط الاستلام بالفاتورة.
- الحسابات المقابلة لجهة التوصيل ورسوم الشحن والمردودات وفروق الجرد.
- تفاصيل الصلاحيات والاعتماد لكل مستند.


## 8.4 مراجعة دليل الحسابات ومفاتيح الربط — تدقيق ساكن

**الحالة:** مراجعة توثيقية على ملفات `main`، وليست اعتمادًا نهائيًا لأرقام الحسابات في النظام الجديد. تمت مطابقة `CHART_OF_ACCOUNTS_SEED.sql` مع وثائق المراحل 11 و12 و14 و15 و17 و23 و29، ومع مصفوفة الأحداث أعلاه.

### ما ثبت وجوده في مرجع الحسابات

1. **مفاتيح الحسابات العامة في Seed:** `CUSTOMERS → 1151`، و`SALES → 4110`، و`COGS → 5110`، و`INVENTORY → 1161`، و`SALES_RETURNS → 4210`، و`SHIPPING_REVENUE → 4120`. هذه روابط موجودة في Seed القديم، وليست إعدادات منفذة أو معتمدة تلقائيًا في Laravel الجديد.
2. **عهدة المندوب وعمولته:** Seed يربط إعداد التسوية بالحسابات `1141` لعهدة المندوب، و`5220` لمصروف العمولة، و`2122` لمستحق العمولة، مع وضع `DEDUCT_FROM_CUSTODY`. وثيقة المرحلة 14 تؤكد أن التحصيل من العميل والتوريد للشركة وصرف العمولة أحداث منفصلة، وأن طريقة التسوية تحفظ على المستند.
3. **طرق الدفع:** وثيقة المرحلة 11 تشترط ربط كل طريقة دفع بحساب معتمد لكل فرع من خلال `payment_method_accounts`، ولا تسمح بالتحويل التلقائي إلى الصندوق عند غياب الربط. الخزائن وطرق الدفع لا تملك ربطًا افتراضيًا آمنًا في Seed.
4. **دفتر الأطراف:** وثيقة المرحلة 12 تقرر أن رصيد الطرف يستخرج من سطور الأستاذ العام باستخدام `partner_type` و`partner_id`، وأن التخصيصات تربط سطرًا مدينًا بسطر دائن ولا تنشئ قيدًا. لا يعود `partners_balance` مصدر حقيقة.
5. **المبيعات والمرتجعات:** اتجاه القيد الموثق هو مدين الطرف المدين/العميل ودائن إيراد المنتجات، ثم مدين تكلفة المبيعات ودائن المخزون للكمية المباعة. المرتجع بعد الاستلام الفعلي يعكس مردودات المبيعات وأثر تكلفة المبيعات. يجب أن يبقى حساب المردودات مستقلًا عن حساب الإيراد؛ وثيقتا المرحلتين 11 و13 سجلتا منع الترحيل إذا تطابق الحسابان.
6. **الشحن:** الحساب `4120` معرف كإيراد الشحن المحصل من العملاء، والحساب `5210` تكلفة شحن الطلبات، و`2121` مستحقات شركات التوصيل. وثيقة المرحلة 29 توثق عند رفض العميل بعد محاولة فعلية: لا يثبت تحصيل رسوم الشحن إلا إذا دفعها العميل، ويكون المدين عهدة المندوب والدائن إيراد الشحن. عمولة محاولة الرفض مستقلة عن التحصيل.
7. **الموردون:** يوجد حساب دليل باسم حسابات الموردين `2111` ودفعات مقدمة للموردين `1171`، لكن Seed المعروض لا يربط مفتاح إعداد عام للموردين ولا يحسم قيد الاستلام/الفاتورة أو مرتجع المورد.

### تعارضات وفجوات يجب عدم تحويلها إلى إعدادات تلقائية

- **رصيد العميل الدائن:** Seed يربط `CUSTOMER_CREDITS` بالحساب `1152` المصنف ضمن الأصول وتحت مجموعة العملاء، بينما يحتوي الدليل أيضًا على `2133` «أرصدة دائنة للعملاء» ضمن الالتزامات، و`2132` «مبالغ مستحقة ردها للعملاء». لا تكفي أسماء الحسابات لتقرير أيها يمثل الرصيد الدائن القابل لإعادة الاستخدام وأيها يمثل مبلغًا مستحق الرد؛ يلزم توحيد نموذج الطرف والتخصيص وتحديد الحساب المقابل قبل الربط.
- **شركة الشحن:** يوجد في الدليل `1142` «مستحقات لدى شركات الشحن» كأصل، و`2121` «مستحقات شركات الشحن» كالتزام. كلاهما قد يلزم بحسب اتجاه العملية: مبالغ محصلة لصالح الشركة لدى الناقل مقابل مبالغ مستحقة الدفع للناقل. لا يجوز اختيار أحدهما تلقائيًا أو الخلط بينه وبين عهدة المندوب `1141`.
- **المخزون بالطريق وتحت الفحص:** الدليل يحتوي `1162` مخزون بالطريق و`1163` مرتجعات تحت الفحص، لكن دورة التحويل بالطريق وحالات الفحص لم تعتمد بعد. وجود الحساب لا يعتمد تلك الحالات ولا يوجب استخدامها.
- **تكاليف الشحن:** وجود `5210` و`2121` لا يحسم هل تُثبت تكلفة شركة الشحن عند إنشاء الشحنة أو عند التسليم أو عند استلام كشف/فاتورة الناقل، ولا كيفية تسوية الخصم من التحصيل مقابل الدفع المنفصل.
- **رسوم الشحن غير المحصلة:** القاعدة التجارية تقرر عدم إنشاء تحصيل وهمي، لكن الحساب المقابل الذي يتحمل تكلفة الشحن عند رفض العميل وعدم الدفع لم يُحسم في وثائق المراحل التي تمت مراجعتها.
- **المشتريات والجرد:** وجود `2111` و`1171` و`5820` لا يعتمد توقيت إثبات المشتريات أو حساب فروق الجرد ولا يحدد قيودها.
- **سياسة التكلفة:** وجود `COGS` و`INVENTORY` أو عمود تكلفة تاريخية في النظام القديم لا يحسم معنى اختيار `other` في النظام الجديد، ولا يجيز افتراض تكلفة يدوية أو FIFO أو متوسط مرجح.

### ما يمكن تثبيته الآن دون حسم طريقة تقييم المخزون

- فصل مفاتيح إيراد المبيعات ومردوداتها وإيراد الشحن عن حسابات التحصيل والتكلفة.
- فصل حساب عهدة المندوب عن حساب مستحقات شركة الشحن الخارجية.
- فصل مصروف عمولة المندوب عن مستحق العمولة، وربط استحقاق العمولة بحدث المحاولة/التسليم المعتمد، لا بوجود تحصيل العميل وحده.
- إلزام ربط كل طريقة دفع بوجهة مالية وحساب GL صالحين للفرع، ومنع fallback إلى الصندوق.
- استخدام حساب مراقبة مشترك للطرف مع تخصيصات الأستاذ بدل إنشاء حساب مستقل لكل عميل/مندوب/مورد، مع حفظ نوع الطرف ومعرفه في سطور القيد.
- عدم إنشاء روابط حسابات أو أرقام افتراضية جديدة في Laravel قبل اعتماد خريطة الحسابات النهائية.

## 8.5 مصفوفة الحسابات المقابلة حسب السيناريو — مسودة ربط

**الحالة:** تحليل ربط وظيفي يستند إلى قواعد التشغيل ومفاتيح Seed القديم. لا يعتمد أرقامًا نهائية ولا ينشئ إعدادات للنظام الجديد. كلمة «مدين/دائن» تصف اتجاه القيد المرشح فقط، وتظل القيود النهائية مرتبطة بتوقيت الحدث ومستند الإثبات.

### قواعد ربط مستخلصة

1. حساب العميل/المورد/المندوب/شركة الشحن هو حساب مراقبة GL، بينما هوية الطرف تحفظ في سطر القيد؛ التخصيص يربط المديونية والتحصيل أو الائتمان ولا ينشئ قيدًا جديدًا.
2. لا تخلط بين **عهدة المندوب** و**مستحقات لدى شركة الشحن** و**مستحقات واجبة الدفع لشركة الشحن**؛ لكل منها اتجاه اقتصادي ومستند إثبات مختلف.
3. لا تخلط بين **إيراد الشحن من العميل** و**تكلفة شركة الشحن**؛ قد يجتمعان في الطلب نفسه لكنهما ليسا حسابًا واحدًا ولا حدثًا واحدًا.
4. لا تثبت التحصيل أو الإيراد من تقرير شركة الشحن وحده؛ يلزم حدث/مستند يثبت المبلغ الذي تم تحصيله فعلًا، ثم مستند التسوية الذي يثبت وصول النقدية.
5. لا تثبت تكلفة المبيعات أو عكسها قبل اعتماد قيمة التكلفة التاريخية للكمية المسلمة/المرتجعة.
6. لا يُعتمد رقم حساب أو مفتاح إعداد نهائي في Laravel الجديد إلا بعد مراجعة شجرة الحسابات وإقرار الحسابات المقابلة لكل حدث، ثم اختبار توازن القيود والتخصيص والعكس.



### تدقيق إضافي للمصفوفة على ضوء تفاصيل دورة المندوب

بعد مطابقة المسودة مع تفاصيل المرحلة 14 والمرحلة 17 والمرحلة 29، تُثبت التوضيحات التالية حتى لا تختلط أحداث المندوب الداخلية بأحداث شركة الشحن الخارجية:

1. **تحصيل العميل لدى المندوب الداخلي:** القيد المؤكد هو مدين عهدة المندوب (طرف من نوع `DELIVERY`) ودائن حساب مراقبة العميل، مع تخصيص سطر الدائن على مديونية أمر/أوامر البيع. لا يُعد هذا توريدًا للشركة؛ توريد المندوب حدث مستقل يقفل العهدة.
2. **استحقاق عمولة المندوب:** القيد المؤكد عند تحقق الاستحقاق هو مدين مصروف عمولة المندوب ودائن مستحقات عمولة المندوب (طرف `DELIVERY`). هذا الاستحقاق مستقل عن قبض رسوم الشحن، ويظل مستحقًا عند محاولة توصيل فعلية مرفوضة حتى لو لم يدفع العميل رسوم الشحن. مبلغ العمولة وأساس احتسابها يظلان حسب السياسة التجارية المعتمدة، ولا يستنتجان من قيمة التحصيل وحدها.
3. **تسوية عهدة المندوب بخصم العمولة:** إذا كانت السياسة الفعلية `DEDUCT_FROM_CUSTODY`، يقفل إجمالي العهدة مقابل صافي النقدية الموردة ومقاصة مستحق العمولة؛ لا ينشأ صرف نقدي للعمولة عند المقاصة. وإذا كانت `SEPARATE`، يورد المندوب كامل العهدة ثم يصرف مستحق العمولة بقيد مستقل. تحفظ طريقة التسوية الفعلية في مستندها.
4. **رفض العميل بعد محاولة فعلية:** إذا دفع العميل رسوم الشحن، مدين عهدة المندوب ودائن إيراد الشحن مرة واحدة لكل طلب. إذا لم يدفع، لا ينشأ قبض ولا عهدة مالية ولا إيراد شحن محصل؛ وتظل تكلفة المحاولة/الشحن التي تتحملها الشركة بحاجة إلى حساب وسياسة معتمدة. العمولة تبقى حدثًا مستقلًا في الحالتين.
5. **استرداد عهدة المنتجات دون محاولة توصيل:** حركة مخزون فقط (من عهدة المندوب إلى المخزن)، دون بيع أو تحصيل شحن أو عمولة أو قيد مالي.
6. **شركة الشحن الخارجية:** لا تطبق عليها قيود عهدة المندوب أو عمولته. يمكن أن يظهر حساب `1142` كذمم/مبالغ لدى الناقل عندما يكون قد قبض أموالًا لحساب الشركة ولم يوردها بعد، بينما يمثل `2121` التزامًا للشركة تجاه الناقل عند استحقاق رسومه. لا يجري إجراء مقاصة أو اختيار حساب تلقائي قبل تحديد مستند إثبات التحصيل وتوقيت استحقاق فاتورة الناقل.
7. **مديونية الشحن:** المرحلة 17 كشفت خللًا تاريخيًا في ربط تحصيل الشحن بسطر مديونية المنتجات فقط. القاعدة التصميمية المرجعية هي فصل سطر مديونية الشحن عن سطر المنتجات، وتخصيص كل تحصيل على السطر الصحيح؛ لا يُسمح بتخصيص قيمة الشحن على سطر المنتجات بما يتجاوز رصيده. هذا تدقيق للسلوك القديم وليس إثباتًا أن مسار Laravel الجديد نفذ ذلك.

**حدود الإثبات:** البنود أعلاه مستخلصة من وثائق المراحل القديمة وكودها الموثق، ولا تعني أن المسارات القديمة مكتملة أو جاهزة للنقل. تبقى خريطة الحسابات النهائية للناقل وتكلفة الشحن غير المحصل ومقدار العمولة وتوقيتها مرتبطة بإغلاق السياسة التجارية والمحاسبية واختبارها.



## 8.7 تدقيق أدلة تكلفة المخزون في النظام القديم

**نوع الدليل:** سلوك قديم مثبت في مراجعة كود وSQL المصدر على `main`، وليس قرارًا معتمدًا للنظام الجديد.

1. تكلفة المنتج القديمة `product_codes.CODE_COST_PRICE` قيمة يدوية مرجعية لكل كود منتج؛ شاشة بيانات المنتج تسمح بإدخالها وتعديلها.
2. عند إنشاء/تعديل بند الطلب، تُنسخ التكلفة إلى `order_product.COST_PRICE`، وتستخدم المحاسبة هذه النسخة التاريخية لحساب تكلفة الكمية المسلمة والمرتجعة.
3. أوامر الشراء تحفظ سعر الشراء الفعلي في `purchases_products.PURCHASE_UNIT_PRICE`، لكن مسار الشراء/الاستلام الذي تمت مراجعته لا يحدّث `CODE_COST_PRICE` تلقائيًا.
4. حركات الاستلام والصرف التي تمت مراجعتها تحدث كميات المخزون؛ لم يظهر فيها احتساب طبقات تكلفة أو FIFO أو متوسط مرجح أو قيمة مالية لرصيد كل مخزن.
5. لذلك لا يصح وصف النظام القديم بأنه يطبق طريقة تقييم مخزون محاسبية. ما يثبته هو تكلفة مرجعية يدوية تُحفظ على بند الطلب، وهي مختلفة عن سعر شراء المورد الفعلي.

### أثر ذلك على قرار `other`

- هذا الدليل يثبت ما كان يفعله النظام القديم فقط؛ ولا يثبت أن اختيار `other` في النظام الجديد يعني اعتماد التكلفة اليدوية.
- إذا اعتمد المستخدم لاحقًا هذا السلوك، فيجب تحديد هل تُثبت التكلفة عند إنشاء الطلب أم عند اعتماده، وكيف تتعامل مع تغيير بند الطلب قبل الترحيل، وهل تمنع التكلفة الصفرية، وكيف تعالج الطلبات القديمة التي لا تحتوي تكلفة.
- لا يجوز تحديث تكلفة الطلبات التاريخية من تكلفة المنتج الحالية، ولا تحويل سعر الشراء إلى تكلفة مرجعية تلقائيًا دون سياسة معتمدة.
- لا يجوز اعتماد قيد تكلفة المبيعات أو عكس تكلفة المرتجع قبل تحديد التكلفة التاريخية التي تخص الكمية الفعلية المسلمة/المستلمة.
- لا تزال هناك حاجة لفحص مسار Laravel الجديد بعد اكتمال وحدة المنتجات والمشتريات؛ لا تتوفر في هذا التدقيق أدلة كافية لإثبات مصدر `COST_PRICE` في النسخة الجديدة.

**النتيجة:** أدلة النظام القديم أصبحت موثقة بما يكفي للمقارنة، لكنها لا تغلق قرار تقييم المخزون. يظل معنى `other` مفتوحًا ولا يبدأ التنفيذ المالي اعتمادًا على هذا الاستنتاج وحده.


## 9. قرارات لا تزال مفتوحة

لا تُعتبر البنود التالية محسومة بمجرد ورودها في هذه الوثيقة:

1. **سياسة تقييم المخزون:** طريقة التكلفة، توقيت تثبيت التكلفة، معالجة تغير تكلفة الاستلام، والتكلفة عند الصرف والمرتجع.
2. **الاستلام:** متى يعتبر الاستلام نهائيًا؟ وهل توجد حالات استلام جزئي أو تحت الفحص أو مرفوض؟
3. **الصرف:** ما الحالات التي تسمح بالصرف؟ وما علاقته بتجهيز الطلب وتسليمه لشركة الشحن أو المندوب؟
4. **الحجز:** متى ينشأ؟ متى ينتهي؟ وكيف يعالج الحجز المتعارض أو منتهي الصلاحية؟
5. **الجرد:** أسلوب الجرد، إيقاف الحركة أو استمرارها، وحدود اعتماد الفروقات.
6. **تتبع المخزون:** هل نحتاج دفعات أو أرقامًا تسلسلية أو صلاحية أو مخزونًا تالفًا/معلقًا؟
7. **العملة والدقة:** العملات المدعومة ودقة الكميات والأسعار والتقريب.
8. **مصفوفة الترحيل:** تحديد كل حدث مخزني له أثر مالي، والحسابات المقابلة، وشروط الترحيل والعكس.
9. **الاعتماد:** فصل الإنشاء والمراجعة والاعتماد والترحيل حسب الدور والفرع.
10. **التكامل:** آلية Outbox/Queue، سياسة إعادة المحاولة، ومراقبة الأحداث الفاشلة.

## 10. ما نحتاج مراجعته قبل اعتماد التصميم التفصيلي

- وثائق الحسابات الموجودة على `main` باعتبارها مرجع المجال المالي فقط، مع مطابقتها بالكود.
- كود المخازن الفعلي في النظام القديم لاستخراج السلوك والحالات، دون اعتباره مواصفة صحيحة تلقائيًا.
- دورة الاستلام والصرف والتحويل والجرد والحجز والمرتجعات.
- صلاحيات المخازن والحسابات والفصل بين الواجبات.
- أمثلة حقيقية من العمليات والمستندات والتقارير بعد إزالة أي بيانات حساسة.

## 11. بوابة الاعتماد قبل التنفيذ

لا يبدأ إنشاء جداول الأعمال أو migrations أو خدمات Laravel للنواتين قبل اعتماد ما يلي:

- حدود مسؤولية كل نواة.
- دورة الحركة المخزنية وحالاتها.
- دورة القيد والترحيل والعكس.
- سياسة تقييم المخزون.
- مصفوفة أحداث المخزون والأثر المالي.
- قواعد الصلاحيات والاعتماد.
- قاموس البيانات وERD.

بعد الاعتماد، تصمم كل نواة على مستوى حالات الاستخدام ثم البيانات والاختبارات، وتنفذ تدريجيًا على `rebuild-v2` دون تعديل `main` أو النشر إلى بيئة الاختبار تلقائيًا.
