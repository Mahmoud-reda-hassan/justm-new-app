# معمارية Just-M V2 — إعادة البناء من الصفر

**الحالة:** تأسيس الهيكل — لا توجد وظائف تشغيلية معتمدة بعد.  
**الفرع:** `rebuild-v2`  
**المرجع:** `main` وملفات توثيق المشروع الحالي، للاكتشاف والتحقق لا للنسخ الأعمى.

## 1. الهدف

إنشاء تطبيق جديد مستقل بهندسة واضحة وقابلة للاختبار والصيانة، مع إعادة بناء دورات العمل تدريجيًا بعد توثيقها واعتمادها. لا يعني "من الصفر" إسقاط قواعد العمل أو البيانات التاريخية؛ بل فصل التنفيذ الجديد عن القديم مع الحفاظ على المتطلبات الصحيحة.

## 2. التقنيات والقيود

- PHP 8.4.
- PDO مع Prepared Statements.
- MariaDB، مع SQL migrations صريحة.
- واجهة عربية RTL متجاوبة.
- لا Laravel ولا Framework مفروض.
- الاعتماد على Composer عند الحاجة فقط، مع تثبيت الإصدارات في lock file.
- لا أسرار أو بيانات اتصال داخل Git.

## 3. الطبقات

| الطبقة | المسؤولية |
|---|---|
| Domain | قواعد العمل والكيانات والقيم والاستثناءات؛ بلا اعتماد على HTTP أو SQL |
| Application | حالات الاستخدام وتنسيق العمليات والمعاملات |
| Infrastructure | PDO والمستودعات والتكاملات والتخزين |
| Presentation | HTTP controllers وواجهات العرض وطلبات/استجابات API |
| Bootstrap | تحميل الإعدادات والاعتماديات وتهيئة التطبيق |

## 5. وحدات المجال

- الهوية والصلاحيات.
- الأطراف والعملاء والموردون.
- المنتجات والتسعير.
- المخزون والحجوزات والحركات.
- المبيعات وأوامر البيع.
- الشحن والتسليم والتحصيل والعهد.
- المرتجعات.
- المحاسبة العامة والأستاذ العام.
- التقارير والإعدادات.

تقسيم الوحدات مبدئي؛ الحدود النهائية تعتمد على تحليل دورة العمل والاعتماديات.

## 6. قواعد معمارية غير قابلة للتجاوز

1. لا تنفذ SQL داخل Domain أو Controllers.
2. لا تعتمد الواجهة على قواعد مالية لحساب الأرصدة.
3. كل عملية مالية مؤثرة تمر عبر خدمة تطبيقية واضحة وتنتج قيود GL متوازنة.
4. لا يُسمح بتكرار ترحيل الحدث؛ تستخدم مفاتيح idempotency.
5. العمليات التي تجمع أثرًا تشغيليًا ومخزنيًا وماليًا تحدد حدود معاملاتها صراحة.
6. لا تُحذف أوامر البيع؛ الإلغاء حدث/حالة مع عكس الآثار حسب قواعد العمل.
7. لا يُرحّل مردود مالي قبل إثبات الاستلام المخزني، وفق الاستثناء المعتمد لإلغاء مقدم العميل قبل التسليم.
8. لا تُخزن كلمات المرور أو مفاتيح التشفير أو بيانات الاتصال في المستودع.
9. جميع مبالغ المال تستخدم DECIMAL، لا FLOAT.
10. كل Migration لها اختبار ترقية، وعند الحاجة خطة تراجع آمنة.

## 7. منهج نقل النظام القديم

- اكتشاف: حصر الشاشات والمسارات والجداول والصلاحيات والأحداث.
- توثيق: وصف السلوك الفعلي مقابل القواعد المطلوبة.
- اعتماد: تسجيل القرارات المفتوحة قبل البرمجة.
- تصميم: حالات الاستخدام ومخططات البيانات والتدفقات.
- تنفيذ: وحدة واحدة في كل مرة.
- اختبار: Unit ثم Integration ثم Acceptance.
- ترحيل: بيانات وخطة مطابقة وتسوية قبل التحويل.
- تشغيل: بيئة اختبار منفصلة ثم قبول المستخدم.

## 8. مبادئ المبيعات المعروفة حتى الآن

أنواع منشئي أمر البيع المعتمدة في متطلبات العمل:
- المسوّق: يسجل طلب العميل؛ سعر داخل نطاق؛ عمولة القطعة المستلمة فعليًا، وتُعكس للقطعة المرتجعة.
- وسيط البيع: ينشئ أمر البيع؛ سعر داخل نطاق؛ الحد الأدنى للشركة والزيادة عمولته.
- العميل: يشتري بنفسه من الموقع؛ سعر القائمة الأعلى مع خصم قد تمنحه الشركة.
- العميل العادي: يشتري مباشرة من منفذ البيع؛ تفاصيل التسعير النهائية تحتاج ربطها بسياسة المنفذ.

هذه متطلبات وليست إثباتًا أن النظام القديم ينفذها.

## 9. القرارات المالية المعروفة

- الأستاذ العام مصدر الحقيقة المالي الوحيد.
- ضريبة القيمة المضافة: غير مطبقة حاليًا.
- الشحن مستقل عن قيمة المنتجات ويحسب مرة واحدة للأمر.
- العمولة تخصم وفق القرار المعتمد، مع فصل أنواع استحقاق المسوق والوسيط.
- المرتجع الجزئي يعالج بالكميات الفعلية، وتنعكس العمولة على القطع المرتجعة.
- لا يتم اعتماد أي قيد أو حساب افتراضي قبل تعريف دليل الحسابات وإعدادات الأحداث.

## 10. بوابة اعتماد قبل بناء الوظائف

لا تبدأ كتابة وظائف المبيعات أو المخزون أو المالية قبل اكتمال:
- سجل الشاشات ودورات العمل.
- مصفوفة الأدوار والصلاحيات.
- قاموس البيانات ومخطط ERD.
- جدول الأحداث التشغيلية والمخزنية والمالية.
- مواصفات حالات الاستخدام ومعايير قبولها.
- تصميم GL وترحيل البيانات.
